# Split onboarding "Tenant configuration" into Configuration + Credentials steps

## Problem
`AccessStep` couples capability selection with credential issuance in one step:
- Once credentials are issued, the switches lock (`disabled={issued}`) — no way to change/update inside the wizard (the user's main complaint).
- The step gives no clarity that pressing the button will *generate credentials*, what a client ID/secret is, or that the secret is shown once.
- Same problems apply when resuming/updating an existing (Pending) institution — it's the same components.

## New wizard structure (5 → 6 steps)
1. **Institution** — unchanged
2. **Configuration** — capability toggles only (NEW)
3. **Credentials** — issuance ceremony (NEW)
4. **Certificate** — unchanged (optional)
5. **Signing key** — unchanged (optional, only when generation is on)
6. **Review** — rows updated

## Step designs

**ConfigurationStep** (replaces the config half of AccessStep):
- Header copy: "Choose what this institution may do. The credentials issued in the next step are scoped to exactly these capabilities."
- The two existing SwitchRows (QR generation / QR validation, scope descriptions unchanged).
- Guard unchanged: at least one capability → warn banner + Continue disabled.
- **Stays editable after issuance** (user's choice): when `access` exists, show info banner "Credentials already issued (Client ID …). Changes here apply to them immediately — no new secret is needed." and toggling patches the store's `access` scope fields directly (clientId/secret untouched) — same semantics as the Manage credentials drawer.
- Pre-issuance changes stay in wizard state only.

**CredentialsStep** (replaces the issuance half):
- Pre-issue: read-only summary of the selected capabilities + plain-language explanation — client ID identifies the institution in every request; client secret authenticates its gateway; the secret is shown **once** (only a hash is kept). Single primary button "Issue credentials".
- Issue: `demoCredentials(code)` (from `institutions/credentials.ts`) → save `access` to store → existing `SecretDialog` ceremony (held until "I have stored the secret").
- Post-issue: ok banner — Client ID, secret shown once; capabilities can be changed from the Configuration step or later from the institution page (rotate/regenerate live there).
- Footer mirrors today: pre-issue shows Back + Issue credentials; post-issue shows Back + Continue.

**ReviewStep**: split the single "API credentials" row into "Capabilities" (e.g. "Generation and validation") and "API credentials" (Client ID or "Not issued").

## onboarding-page.tsx
- `StepId` gains `'configuration' | 'credentials'` (drops `'access'`); steps array becomes 6 entries.
- New wizard state `config: {generation, validation}` initialized from `existing?.access ?? {generation: true, validation: true}`; existing `access` state unchanged.
- `firstIncomplete`: `!i.access → 'configuration'`; certificate/key/review logic unchanged (resume of inst-4 still lands on Certificate).
- Handlers: config-change (wizard state; store patch when issued), issue (demoCredentials + SecretDialog).

## steps.tsx
- Delete `AccessStep`; add `ConfigurationStep` + `CredentialsStep`; update `ReviewStep` rows. The one-line hint added earlier to the AccessStep banner moves into CredentialsStep's post-issue copy.

## Consistency
- Active-institution editing (Manage credentials drawer, built earlier this session) already implements the same stay-editable + rotate/regenerate semantics — no changes needed there.
- Stepper component handles any step count (mobile shows "Step n of N"); 6 short labels fit the max-w-2xl layout.

## Tests (onboarding.test.tsx updates + additions)

- Rework validate-only flow: generation off at Configuration → issue → certificate skip → Review has no signing-key row → Finish later.
- Resume test (inst-4) unchanged expectation.
- NEW: after issuing, Back to Configuration, flip a capability → store `access` updates (scope changed, clientId unchanged).
- NEW: Credentials step shows the chosen capabilities before issuing (clarity check).

## Known limitation (accepted)
Pre-issuance capability choices are wizard-local: abandoning the wizard and resuming resets them to defaults (or to the issued scopes once issued) — the in-memory store has no draft-config field; the real API will commit each step.
