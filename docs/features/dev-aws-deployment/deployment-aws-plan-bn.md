**মূল কৌশল ৫টি:**

1. **ব্যবসায়িক কম্পোনেন্ট (API, DB, Vault, Portal)** — Production-এর আকৃতিতে (shape) বানাব, শুধু ছোট সাইজে। যাতে পরে "আকার বাড়ানো" যায়, "নতুন করে বানাতে" না হয়।
2. **টেস্ট-সহায়ক কম্পোনেন্ট (Gateway, IdP)** — সব FI-এর জন্য **একটাই ছোট সার্ভার**, আলাদা Container। প্রতি FI-তে আলাদা সার্ভার নয়।
3. **ব্যয়বহুল জিনিস এড়াব** — NAT Gateway (~$43/মাস), Load Balancer (~$18+/মাস), Secrets Manager — Dev-এ এগুলো ছাড়াই নিরাপত্তা বজায় রাখা সম্ভব।
4. **নিরাপত্তায় কোনো আপস নয়** — ডাটাবেস ইন্টারনেটে খোলা নয়, SSH পোর্ট বন্ধ, Vault প্রাইভেট ও এনক্রিপ্টেড, স্থায়ী Access Key নয়।
5. **সব কিছু Code হিসেবে (IaC)** — Terraform দিয়ে লিখব; ফলে Staging/Prod একই কোড থেকে বানানো যাবে, আর Dev নষ্ট হলে মিনিটে আবার তৈরি হবে।

## ২. মূল শব্দগুলো (শুরুতে এটুকু জানলেই চলবে)

| শব্দ | সহজ ব্যাখ্যা |
|---|---|
| **AWS** | Amazon-এর ভাড়া-নেওয়া কম্পিউটার ও সেবার প্ল্যাটফর্ম। ঘণ্টা/ব্যবহার অনুযায়ী বিল হয়। |
| **EC2** | AWS-এ ভাড়া করা একটি ভার্চুয়াল সার্ভার। সাইজ ভেদে নাম: `t3.medium` (২ vCPU, ৪ GB RAM) ইত্যাদি। |
| **RDS** | AWS-এর "ম্যানেজড ডাটাবেস" — ব্যাকআপ, প্যাচ, ফেইলওভার AWS সামলায়। |
| **Single-AZ / Multi-AZ** | AZ = একই শহরের আলাদা ডাটা সেন্টার। Single-AZ = একটাই (সস্তা, ডাউনটাইমের ঝুঁকি)। Multi-AZ = দ্বিতীয় ডাটা সেন্টারে হট-কপি, একটি নষ্ট হলে অটো-সুইচ (খরচ ~২ গুণ)। |
| **S3** | ফাইল রাখার অনেক-টেকসই স্টোরেজ। "Bucket" = ফোল্ডারের মতো পাত্র। |
| **CloudFront (CDN)** | সারা পৃথিবীর এজ-সার্ভারে ওয়েবসাইট ফাইল রেখে দ্রুত ও সস্তায় পরিবেশন করে; ফ্রি-টায়ারে প্রতি মাসে ১ TB ট্রাফিক। |
| **VPC / Subnet** | AWS-এর ভেতরে আমাদের নিজস্ব ব্যক্তিগত নেটওয়ার্ক। Public subnet = ইন্টারনেটের সাথে যুক্ত; Private subnet = ইন্টারনেট থেকে অদৃশ্য। |
| **Security Group (SG)** | প্রতিটি রিসোর্সের "ফায়ারওয়াল" — কে কোন পোর্টে ঢুকতে পারবে তার তালিকা। |
| **IAM Role** | "এই সার্ভার শুধু অমুক Bucket পড়তে/লিখতে পারবে" — পাসওয়ার্ড ছাড়াই অনুমতি। |
| **Docker Container** | অ্যাপ + তার দরকারি সবকিছু একটি প্যাকেটে। একই সার্ভারে অনেকগুলো আলাদাভাবে চালানো যায়। |
| **Reverse Proxy (Caddy)** | সার্ভারের "রিসেপশনিস্ট" — বাইরে থেকে আসা অনুরোধ দেখে ঠিক Container-এ পাঠায় এবং HTTPS সার্টিফিকেট নিজে থেকে নেয়/নবায়ন করে। |
| **IaC (Terraform)** | ক্লিক করে নয়, কোড লিখে অবকাঠামো বানানো — পুনরাবৃত্তিযোগ্য ও রিভিউযোগ্য। |
| **FI** | Financial Institution (ব্যাংক/MFS)। **Gateway** = FI-র মোবাইল অ্যাপ ও RVL API-এর মাঝের নিরাপদ সেতু। **IdP** = FI-র "লগইন সার্ভার" (ব্যবহারকারী চেনার জন্য)। |

## ৩. সিস্টেমটা কীভাবে কাজ করে (Dev-এ)

```
                        ইন্টারনেট
   ┌────────────────────┼──────────────────────────────┐
   │                    │                              │
 ব্রাউজার          FI মোবাইল অ্যাপ/Emulator       টেস্টার
(Portal)                │                              │
   │                    │ (১) লগইন                      │
   ▼                    ▼                              │
CloudFront ───┐   ┌─ idp-<fi>.dev…  (FI IdP Mock) ◄────┘
 (Portal ফাইল │   │       │ JWT টোকেন
  S3 থেকে)    │   ▼       ▼
              │  gw-<fi>.dev…  (FI Gateway)  ← শেয়ার্ড টেস্ট-হোস্ট (১টি EC2)
              │       │ (২) টোকেন + QR অনুরোধ
   /v1/* ─────┴───────┼──────────────┐
                      ▼              │
              api.dev.sbqr…  (SBQR.API) ← EC2 (Elastic IP)
                      │      │
            ┌─────────┘      └──────────┐
            ▼ (Private subnet)          ▼
        RDS PostgreSQL            S3 Certificate Vault
        (ইন্টারনেটে অদৃশ্য)        (প্রাইভেট, এনক্রিপ্টেড)
```

**পড়ার ক্রম:** ব্যবহারকারী FI-র IdP-তে লগইন করে JWT পায় → Gateway সেই JWT যাচাই করে এবং RVL API-কে ডাকে → API ডাটাবেসে হিসাব রাখে ও Vault-এর কী (key) দিয়ে QR সই (sign) করে। Portal ব্রাউজার থেকে সরাসরি API-কে ডাকে (CloudFront-এর মাধ্যমে)।

## ৪. রিসোর্স-ভিত্তিক বিস্তারিত পরিকল্পনা

### ৪.০ ভিত্তি: নেটওয়ার্ক, নাম, অ্যাকাউন্ট

- **নাম:** `rvl-sbqr-<রিসোর্স>-dev` (বিদ্যমান নিয়ম অনুযায়ী, `deployments.md`)।
- **VPC:** একটি আলাদা VPC (`rvl-sbqr-vpc-dev`)।
  - ২টি **Public subnet** (API ও টেস্ট-হোস্টের জন্য), ২টি **Private subnet** (ডাটাবেসের জন্য, ২টি AZ কারণ RDS-এর নিয়ম)।
  - ❌ **NAT Gateway বানাব না** (~$43/মাস অপচয়)। Private subnet-এ শুধু ডাটাবেস থাকবে, তার ইন্টারনেট লাগে না।
  - ✅ **S3 Gateway Endpoint** (বিনামূল্যে) — যাতে Vault-এর ট্রাফিক AWS-এর ভেতরেই থাকে।
- **AWS অ্যাকাউন্ট:** সম্ভব হলে Dev ও Prod **আলাদা AWS অ্যাকাউন্টে** (AWS Organizations — বিনামূল্যে)। Dev-এ ভুল হলে Prod-এ প্রভাব পড়ে না।
- **Tagging:** সব রিসোর্সে `Project=SBQR`, `Env=dev`, `Owner`, `CostCenter` ট্যাগ — যাতে খরচ ভাগ করে দেখা যায়।

| বিষয় | সিদ্ধান্ত | কারণ |

| নেটওয়ার্ক | Private subnet, Public access = **No** | ইন্টারনেট থেকে ডাটাবেসে ঢোকা অসম্ভব |
| ফায়ারওয়াল | `rvl-sbqr-db-sg-dev`: **শুধু API-র SG থেকে** ৫৪৩২ | আর কেউ (টেস্ট-হোস্টও না) ডাটাবেস ছুঁতে পারবে না |
| এনক্রিপশন | At-rest চালু (AWS-managed key, বিনামূল্যে) + `rds.force_ssl=1` | ডেটা ও যাতায়াত দুটোই সুরক্ষিত |

| মাইগ্রেশনের আগে | ম্যানুয়াল Snapshot | `db/migrations/*.sql` ব্যর্থ হলে দ্রুত ফেরা |
| পাসওয়ার্ড | RDS-এর নিজস্ব managed master secret **বা** SSM SecureString | কোডে/Git-এ পাসওয়ার্ড নয় |
| মনিটরিং | CloudWatch: CPU, Free storage, Connections অ্যালার্ম | সমস্যা আগে ধরা |

> **খরচ-টিপ:** Dev-এ রাত/সাপ্তাহিক ছুটিতে RDS **Stop** করা যায় (EventBridge Scheduler দিয়ে)। মনে রাখতে হবে — AWS ৭ দিন পর নিজে থেকে আবার চালু করে দেয়, তাই Scheduler-ই নিয়ন্ত্রণ করবে।

### ৪.৩ SBQR Gateway — একাধিক FI, সবচেয়ে সস্তা উপায়

**সমস্যা:** Gateway প্রতি FI-র জন্য আলাদা কনফিগারেশনে চলে (আলাদা IdP-র ঠিকানা `Auth__Authority`, আলাদা `Platform__ClientId/Secret`)। অর্থাৎ ৫টি FI = ৫টি Gateway। প্রতিটির জন্য আলাদা সার্ভার ভাড়া করা অপচয়, কারণ প্রতিটি Gateway খুব হালকা (~১৫০–২০০ MB RAM, প্রায় সময় অলস)।

**বিকল্প তুলনা (৫টি FI ধরে, Gateway + IdP উভয়সহ, আনুমানিক):**

| বিকল্প | কীভাবে | মাসিক খরচ | মন্তব্য |
|---|---|---|---|
| A. প্রতি FI-তে আলাদা EC2 | ৫ × `t4g.micro` + EBS + IP | ~$70+ | সহজ আলাদা-করণ, কিন্তু সবচেয়ে অপচয়ী |
| B. ECS Fargate | ১০টি ছোট Task (Gateway ও IdP আলাদা) + Load Balancer | ~$130 | কোনো সার্ভার সামলাতে হয় না, কিন্তু Dev-এর জন্য দামি |
| C. Fly.io (বর্তমানে ব্যবহৃত) | স্কেল-টু-জিরো, অলস থাকলে প্রায় শূন্য খরচ | ~$0–10 | AWS-এর বাইরে; ডক "free tier" বললেও Fly-এর বর্তমান বিলিং শর্ত যাচাই করতে হবে; API-র সাথে আলাদা ক্লাউডে — নেটওয়ার্ক-নীতি বিভক্ত |
| **D. ✅ একটি শেয়ার্ড EC2 + Docker Compose** | ১টি `t4g.small`; প্রতি FI-তে ২টি Container; Caddy সামনে | **~$22 (ফ্ল্যাট)** | **সুপারিশকৃত** — FI বাড়লে খরচ প্রায় বাড়ে না |

**সুপারিশ: বিকল্প D** — কারণ: (ক) সবটাই AWS-এ, একই নিরাপত্তা-সীমানায়; (খ) FI যোগ করা = `compose` ফাইলে ১টি সেকশন যোগ; (গ) Fly থেকে এসে `Dockerfile` একই থাকছে, কোড বদলাতে হয় না। (C) **ফলব্যাক** হিসেবে থাকবে।

**নকশা (টেস্ট-হোস্ট `rvl-sbqr-testhost-dev`):**

```
t4g.small (২ GB RAM) — একটি Elastic IP
└─ Caddy (পোর্ট ৮০/৪৪৩; হোস্টনেম দেখে রাউট করে, সার্টিফিকেট অটো)
    ├─ gw-dhakabank.dev.sbqr.<domain>  → container: gw-dhakabank  (:8080)
    ├─ idp-dhakabank.dev.sbqr.<domain> → container: idp-dhakabank (:8080)
    ├─ gw-ebl.dev.sbqr.<domain>        → container: gw-ebl
    ├─ idp-ebl.dev.sbqr.<domain>       → container: idp-ebl
    └─ … (প্রতি নতুন FI = আরও ২টি Container + ২টি লাইন)
```

- **DNS:** `*.dev.sbqr.<domain>` একটি ওয়াইল্ডকার্ড রেকর্ড → এই Elastic IP। নতুন FI-র জন্য DNS বদলাতে হয় না।
- **মেমরি সীমা:** প্রতি Gateway Container-এ `mem_limit: 256m`, প্রতি IdP-তে `128m`। এতে একটি Container ঝামেলা করলেও বাকিরা বাঁচে। ২ GB-তে ~৪টি FI আরামে; ৫টির বেশি হলে `t4g.medium` (~$30) — তখনও মোট ~$37, FI-প্রতি ~$6।
- **আর্কিটেকচার-নোট:** `t4g` = ARM। `docker buildx` দিয়ে `linux/arm64` ইমেজ বানাতে হবে (.NET 8 ও Node 20 উভয়ই সমর্থিত)। সমস্যা হলে `t3.small` (~$19) দিয়ে x86-এ ফিরব।
- **সিক্রেট:** প্রতি FI-র `Platform__ClientSecret`, `Idempotency__Salt` ইত্যাদি SSM-এ আলাদা path-এ (`/sbqr/dev/gw/<fi>/…`); BootGuard `REPLACE_WITH_*` ধরলে Container চালুই হবে না — এটি কাঙ্ক্ষিত নিরাপত্তা।
- **ধারাবাহিকতা:** Gateway টোকেন ক্যাশ মেমরিতে রাখে (ডিস্ক/ডাটাবেস লাগে না) → Container মুছে আবার বানানো নিরাপদ, কোনো ডেটা হারায় না।
- **Production-এ নেই:** এই হোস্ট Terraform-এর আলাদা মডিউলে (`module.testhost`), Prod-এ সেটি আদৌ ডিপ্লয় হবে না।

### ৪.৪ FI IdP (Mock)

- **কী:** আসল FI-র লগইন সার্ভারের অনুকরণ (`/connect/token`, OIDC discovery, JWKS)। প্রতি FI-র জন্য একটি ইনস্ট্যান্স (`FI_ID`, `FI_NAME`, আলাদা issuer ও সাইনিং কী)।
- **কোথায়:** ৪.৩-এর **একই শেয়ার্ড হোস্টে**, Node.js Container — আলাদা কোনো খরচ নেই (~৫০–৮০ MB RAM)।
- **গুরুত্বপূর্ণ নিরাপত্তা-সিদ্ধান্ত:**
  - এর ইউজার/পাসওয়ার্ড প্রকাশ্য নকল ডেটা — **কখনো আসল ডেটা বা Prod-এর কাছাকাছি কিছু নয়।**
  - ইন্টারনেটে প্রকাশ্য থাকতেই হবে (Gateway `RequireHttpsMetadata=true` দিয়ে HTTPS-এ JWKS আনে), তাই: ডেডিকেটেড SG, এই হোস্টের IAM Role-এ **কোনো** অনুমতি নেই (Vault/ডাটাবেস অগম্য), `X-Robots-Tag: noindex`।
  - সম্ভব হলে টেস্টার অফিস/VPN IP-তে `idp-*` হোস্টনেমের Caddy-তে allow-list।
  - Prod-এ এর অস্তিত্বই থাকবে না — `Auth__Authority` আসল FI-র IdP-র দিকে যাবে।

### ৪.৫ SBQR Portal (ওয়েব পোর্টাল)

Portal একটি **React/Vite স্ট্যাটিক অ্যাপ** (`npm run build` → `dist/` ফোল্ডার)। অর্থাৎ নিজের কোনো সার্ভার লাগে না — শুধু ফাইল পরিবেশন।

| বিষয় | সিদ্ধান্ত |
|---|---|
| হোস্টিং | **S3 (প্রাইভেট) + CloudFront** (OAC দিয়ে — Bucket সরাসরি ইন্টারনেটে খোলা নয়) |
| খরচ | CloudFront-এর বিনামূল্যে সীমা (১ TB + ১ কোটি অনুরোধ/মাস) ও ক্ষুদ্র S3 — Dev-এ প্রায় $0–2 |
| ডোমেইন / HTTPS | `portal.dev.sbqr.<domain>`; ACM সার্টিফিকেট (বিনামূল্যে, `us-east-1`-এ বানাতে হবে — CloudFront-এর নিয়ম) |
| API সংযোগ | CloudFront-এ ২টি Origin: ডিফল্ট = S3; `/v1/*` ও `/openapi/*` = `api.dev.sbqr…` (ক্যাশ বন্ধ, কুকি/Authorization ফরোয়ার্ড) |
| **কেন একই ডোমেইনে?** | Portal-এর লগইনের Refresh Token একটি `HttpOnly` কুকি (`sbqr_rt`, `Path=/v1/auth`)। ব্রাউজার ও API একই ডোমেইনে থাকলে CORS-জটিলতা ও কুকি-ফাঁসের ঝুঁকি কমে। বর্তমান `vercel.json`-এর `rewrites` ঠিক এটাই করে — CloudFront-এ তার সমতুল্য |
| SPA রাউটিং | `/dashboard` ধরনের URL-এ `index.html` দেখাতে একটি **CloudFront Function** (সব 403/404-কে `index.html` বানিয়ে দেওয়া যাবে না, কারণ তাহলে API-র আসল 404-ও নষ্ট হবে) |
| নিরাপত্তা হেডার | `vercel.json`-এর CSP, `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy`, `Permissions-Policy` CloudFront **Response Headers Policy**-তে হুবহু তুলে নেব |
| ক্যাশ | `/assets/*` → ১ বছর `immutable`; `index.html` → ক্যাশ নয় |
| ডিপ্লয় | CI: `npm ci && npm run build` → `aws s3 sync dist/` → CloudFront invalidation (`/index.html`) |
| বিকল্প | বিদ্যমান **Vercel** চালু থাকতে পারে (দ্রুত ফলব্যাক)। তবে Vercel Hobby প্ল্যান বাণিজ্যিক কাজের জন্য নয় — তাই Pre-UAT থেকে AWS-এ আসা ভালো |

### ৪.৬ Certificate Vault (S3)

এখানে রাখা হয় QR সই করার গোপন কী (Ed25519) ও সার্টিফিকেট — **এটিই সিস্টেমের সবচেয়ে স্পর্শকাতর ডেটা**। (কোডে কী-গুলো আবার KEK দিয়ে অ্যাপ-স্তরে এনক্রিপ্ট হয়; S3 সেটার ওপর দ্বিতীয় স্তর।)

| নিয়ন্ত্রণ | Dev | Prod (পরে) |
|---|---|---|
| Bucket | `rvl-sbqr-key-vault-dev` | `rvl-sbqr-key-vault-prod` |
| Public Access | সব ৪টি ব্লক চালু | একই |
| এনক্রিপশন | SSE-S3 (বিনামূল্যে) | SSE-KMS + নিজস্ব CMK + Bucket Key (~$1/মাস) |
| Versioning | চালু (ভুল ওভাররাইট/মুছে ফেলায় ফেরত আনা যায়) | চালু + MFA Delete/Object Lock বিবেচ্য |
| Lifecycle | পুরনো ভার্সন ৩০ দিন পর মুছবে (খরচ নিয়ন্ত্রণ) | ৯০+ দিন / নীতি অনুযায়ী |
| Bucket Policy | `aws:SecureTransport=false` হলে Deny; শুধু API-র Role অনুমোদিত | একই + VPC Endpoint শর্ত |
| ক্রস-রিজিয়ন কপি | না | বিবেচ্য (DR) |
| লগিং | CloudTrail Data Events শুধু এই Bucket-এ (সীমিত, সস্তা) | চালু |

**অ্যাক্সেস পদ্ধতিতে একটি প্রস্তাবিত পরিবর্তন:** `deployments.md` একটি IAM **User** (স্থায়ী Access Key) বলেছে। আমি সুপারিশ করছি **EC2 Instance Role** (`rvl-sbqr-s3-dev` নামেই) — স্থায়ী চাবি ফাঁস হওয়ার ঝুঁকি শূন্য, চাবি ঘোরানোর ঝামেলা নেই।
✔ কোডে যাচাই করা হয়েছে: `S3ObjectStorage` বলছে `Storage:AccessKeyId/SecretAccessKey` **ফাঁকা রাখলে** AWS-এর ডিফল্ট ক্রেডেনশিয়াল চেইনে ফিরে যায় — অর্থাৎ কোড বদলাতে হবে না, শুধু `sbqr.env`-এ ওই দুটি মান না দিলেই হলো। (Policy-তে অনুমতি: `s3:GetObject/PutObject/DeleteObject/ListBucket` শুধু এই Bucket ও `keycustody/` prefix-এ।)

## ৬. Production-এ উচ্চ ট্রানজ্যাকশনের জন্য যাত্রা (Dev-এ যা প্রমাণ করব)

Dev ছোট, কিন্তু আকৃতি একই রাখার কারণে Prod-এ "বাড়ানো" হবে — "নতুন করে ভাবা" নয়।

| উপাদান | Dev (এখন) | Prod (লক্ষ্য) |
|---|---|---|
| API | ১টি EC2 | ≥২টি EC2 (২ AZ-তে) Auto Scaling Group + **Application Load Balancer** (ALB) + ACM সার্টিফিকেট; CPU/Request-ভিত্তিক স্কেলিং |
| ডাটাবেস | Single-AZ `t4g.small` | **Multi-AZ**, `db.m7g/r7g` শ্রেণি (লোড-টেস্ট অনুযায়ী), Deletion Protection, ৩৫ দিন ব্যাকআপ, Performance Insights, **RDS Proxy** (কানেকশন পুলিং — সার্ভার বাড়লে ডাটাবেস যাতে কানেকশনে না ডোবে), প্রয়োজনে Read Replica রিপোর্টিংয়ের জন্য |
| নেটওয়ার্ক | Public subnet-এ EC2 | EC2 Private subnet-এ; শুধু ALB পাবলিক; NAT-এর বদলে VPC Endpoint (S3, SSM, CloudWatch) যেখানে সম্ভব |
| Vault | SSE-S3 | SSE-KMS (CMK), Object Lock/ক্রস-রিজিয়ন কপি, Data Events লগ |
| Portal | CloudFront + S3 | একই + AWS WAF (রেট-লিমিট, ম্যানেজড রুল) |
| সিক্রেট | SSM Parameter | Secrets Manager (অটো-রোটেশন) বা KMS-সহ SSM |
| মনিটরিং | মৌলিক অ্যালার্ম | ড্যাশবোর্ড, p95/p99 latency, SLO, On-call, GuardDuty, Security Hub |
| খরচ-অপ্টিমাইজেশন | On-Demand | বেসলাইন লোডের জন্য **১ বছরের Compute Savings Plan / RDS Reserved Instance (~৩০–৪০% সাশ্রয়)**; পিক লোডের জন্য On-Demand/Auto Scaling |
| Gateway / IdP | টেস্ট-হোস্টে | **নেই** (FI-রা নিজেদের ইন্টিগ্রেশন চালাবে; Prod-এর `Auth__Authority` আসল FI IdP) |

**Prod-এ "খরচ না বাড়িয়ে পারফরম্যান্স" আনার উপায়:**
1. **আগে মাপো, পরে কেনো:** Pre-UAT-তে k6/JMeter লোড-টেস্ট চালিয়ে সীমা জানব। টেস্টের কয়েক ঘণ্টার জন্য **অস্থায়ীভাবে** বড় সাইজ (যেমন `db.r6g.large`) ভাড়া করব, শেষে ফেরত — ঘণ্টা-হিসাবে বিল, তাই কয়েক ডলারে প্রমাণ মেলে।
2. **ডাটাবেসই বাধা হয়:** ইনডেক্স, কানেকশন পুল, ধীর কোয়েরি (Performance Insights) আগে ঠিক করা — হার্ডওয়্যার বাড়ানোর চেয়ে সস্তা।
3. **Vault-এর কী মেমরিতে ক্যাশ:** প্রতি অনুরোধে S3 ডাকা নয় (কোড আগে থেকেই KEK-ভিত্তিক স্টোর; নিশ্চিত করতে হবে ক্যাশ আছে কি না — §৮ খোলা প্রশ্ন)।
4. **Graviton (ARM)** ব্যবহারে ~২০% সাশ্রয়, একই পারফরম্যান্স।
5. **স্ট্যাটিক কন্টেন্ট CloudFront-এ** — API সার্ভারে লোড কমে।
