অংশ ১

ছয়টি টেবিল এক নজরে

টেবিলএক লাইনে উদ্দেশ্যধরন
usage_eventsস্থায়ী খাতা: প্রতিটি QR operation-এর ঠিক একটি অপরিবর্তনীয় row, লেখার সময়েই বিলযোগ্য চিহ্নসহMetering
billing_rate_cardsদামের তালিকা: প্রতি FI-র ইউনিট-দাম, ভবিষ্যৎ মাসের ১ তারিখ থেকে কার্যকর — append-onlyBilling
billing_periodsমাসের রেজিস্টার: ঢাকা সময়ের প্রতি ক্যালেন্ডার মাসে এক row; এর status-ই সেই মাসের সব statement-এর অবস্থাBilling
billing_statementsএক FI-র এক মাসের বিল, ব্যবহৃত দামের কপিসহBilling
billing_statement_linesমোট কীভাবে এল: প্রতি meter-এ একটি USAGE লাইন, প্রতি adjustment-এ একটি লাইনBilling
billing_adjustmentsCredit/debit — চূড়ান্ত বিল পরের বিলে শোধরায়; অপরিবর্তনীয়, ঠিক একবার প্রয়োগBilling
 
usage_events --(মাস শেষে billable row গুনে, meter অনুযায়ী)--> billing_statement_lines
                                                           x  billing_rate_cards   (কার্যকর দাম)
                                                           +  billing_adjustments  (অপেক্ষমাণ credit/debit)
billing_periods  (মাস + status)  ----------------------->  =  billing_statements   (এক FI, এক মাস)

অংশ ২

টেবিল — উদ্দেশ্য ও column

usage_events — ব্যবহারের খাতা Metering

প্ল্যাটফর্ম যে প্রতিটি QR generation ও validation করে, তার ঠিক একটি row এখানে — যে FI কাজটি চেয়েছে তার নামে। “কী ব্যবহার হয়েছে” প্রশ্নের একমাত্র উৎস এই টেবিল: বিলিং এটাকে গোনে, রিপোর্ট এটা পড়ে, dispute এটা দিয়ে প্রমাণ হয়। Row একবার লেখা হয়, আর কখনো বদলায় না — অডিট-উপযোগী ব্যবহারের ইতিহাস।

ColumnTypeউদ্দেশ্য
usage_event_iduuidPK
tenant_iduuidযে FI-র বিলে গোনা হবে (অনুরোধকারী / যাচাইকারী FI)
meter_codevarchar(40)GENERATION_STATIC / GENERATION_DYNAMIC / VALIDATION
billablebooleanলেখার সময়েই ঠিক: নিশ্চিত verdict ⇒ true, protocol rejection ⇒ false
detailvarchar(40)Validation-এর verdict; generation-এ NULL
source_type / source_idvarchar(30) / uuidকোন QR operation — দুটো মিলে UNIQUE (ঠিক একবারই গোনা)
source_event_iduuidকোন outbox event থেকে এলো (শুধু tracing)
client_referencevarchar(100)FI-র নিজের idempotency key / request id
occurred_at / recorded_attimestamptzকখন ঘটেছে (বিলিং মাস এটাই ঠিক করে) / কখন রেকর্ড হলো

billing_rate_cards — দামের তালিকা Billing

প্রতি FI-র, প্রতি ইউনিটের দাম — ভবিষ্যৎ মাসের ১ তারিখ থেকে কার্যকর। Row append-only এবং মাস ধরে খোঁজা হয় বলে দাম বাড়ানো-কমানো কখনো পুরনো বা চলমান মাসকে নিঃশব্দে নতুন দামে আনে না — নতুন row তার effective_from থেকে দায়িত্ব নেয়। কোনো মাসে কার্যকর card না থাকা FI-র ব্যবহার রেকর্ড হয়, চার্জ হয় না।

ColumnTypeউদ্দেশ্য
rate_card_iduuidPK
tenant_iduuidকোন FI (effective_from-এর সাথে UNIQUE)
effective_fromdateকোন মাস থেকে কার্যকর — সবসময় ১ তারিখ, সবসময় ভবিষ্যৎ মাস
generation_rate / validation_ratenumeric(18,4)প্রতি QR তৈরি / প্রতি validation-এর দাম (BDT)
currency / created_by / created_atchar(3) / auditBDT; কে কখন দাম দিল

billing_periods — মাসের রেজিস্টার Billing

ঢাকা সময়ের প্রতি ক্যালেন্ডার মাসে একটি row। Statement-এর নিজের status নেই: পুরো মাস একসাথে draft, recalculate ও finalize হয়, আর “অক্টোবর চূড়ান্ত” কথাটা ঠিক এক জায়গায় থাকে। Recalculate/finalize চলার সময় এই row lock থাকে, তাই একই মাসে দুটো কাজ পাশাপাশি চলতে পারে না।

ColumnTypeউদ্দেশ্য
periodchar(7)PK — YYYY-MM
statusvarchar(15)DRAFT → FINALIZED; পুরো মাসের immutability trigger এটা চালায়
drafted_attimestamptzকখন স্বয়ংক্রিয় Draft হলো (মাস শেষ + grace + usage সম্পূর্ণ)
finalized_at / finalized_bytimestamptz / varcharকে কখন মাস অনুমোদন করল — চূড়ান্ত হলে বাধ্যতামূলক

billing_statements — এক FI-র মাসিক বিল Billing

প্রতি বিলযোগ্য FI-র, প্রতি মাসে এক row। বিলিংয়ের সময় ব্যবহৃত দামের একটি কপি রাখে, সাথে তার লাইনগুলোর হিসাব। ঋণাত্মক মোট বৈধ অবস্থা (credit), ভুল নয়।

ColumnTypeউদ্দেশ্য
statement_iduuidPK
tenant_id + perioduuid + char(7)কোন FI, কোন মাস — দুটো মিলে UNIQUE (মাসে এক বিল); FK → periods
rate_card_iduuidFK (tenant_id-র সাথে composite) → ব্যবহৃত rate card — শুধু একই FI-র
generation_rate / validation_ratenumeric(18,4)ব্যবহৃত দামের কপি; পরের দাম বদল এই বিলে পৌঁছায় না
subtotal / adjustments_total / totalnumeric(18,2)USAGE লাইন / ADJUSTMENT লাইন / দুটোর যোগফল
currency / calculated_atchar(3) / timestamptzBDT; শেষ হিসাবের সময়

billing_statement_lines — মোট কীভাবে এল Billing

বিলের ভেতরের লাইন: প্রতি meter-এ একটি USAGE লাইন (যাতে FI static, dynamic ও validation আলাদা দেখে) এবং প্রতি প্রয়োগ-করা adjustment-এ একটি লাইন। লাইন কখনো আপডেট হয় না — recalculate সব মুছে নতুন লেখে, তাই draft মাস সবসময় খাতার সাথে মিলে থাকে।

ColumnTypeউদ্দেশ্য
statement_id + line_nouuid + intComposite PK; FK → statements (ON DELETE CASCADE)
line_typevarchar(15)USAGE বা ADJUSTMENT
meter_codevarchar(40)USAGE: কোন meter (এক বিলে প্রতি meter এক লাইন)
adjustment_iduuidADJUSTMENT: FK → adjustments, সব বিল মিলিয়ে unique
descriptionvarchar(200)বিলে যা ছাপা হবে
quantity / unit_rate / amountbigint / numeric(18,4) / numeric(18,2)সংখ্যা × দাম, প্রতি লাইনে একবার rounding

billing_adjustments — credit ও debit Billing

চূড়ান্ত বিল শোধরানোর একমাত্র পথ: কারণ-লেখা, অপরিবর্তনীয় একটি অঙ্ক, যা Pending অবস্থায় অপেক্ষা করে এবং পরের statement-এর মাস চূড়ান্ত হওয়ামাত্র ঠিক একবার সেই বিলে বসে। ভুল adjustment উল্টো অঙ্কের adjustment দিয়ে বাতিল হয় — অডিট ট্রেইলে কোনো ফাঁক থাকে না।

ColumnTypeউদ্দেশ্য
adjustment_iduuidPK
tenant_iduuidকোন FI
amountnumeric(18,2)+ বাড়তি চার্জ / − credit, কখনো 0 নয়
reasonvarchar(500)বাধ্যতামূলক লিখিত কারণ
created_by / created_atauditকে কখন লিখল
applied_statement_iduuidNULL = Pending; একবারই মান পায় (composite FK, একই FI) — যে statement-এর মাস চূড়ান্ত হয়

অংশ ৩

সম্পর্ক

সব কঠোর নিশ্চয়তা Billing-এর ভেতরে আসল foreign key হিসেবে আছে। usage_events ও tenants-এর দিকের সংযোগ ইচ্ছাকৃতভাবে শুধু id reference — কোনো FK module সীমানা পার করে না, তাই Metering ও Tenancy বদলালেও Billing-এর schema আবার lock হয় না।

#কোথা থেকেকোথায়Cardinalityযেভাবে রক্ষিতব্যবসায়িক মানে
১tenantsusage_events1:Mtenant_id (FK নেই)এক FI-র ব্যবহারের ইতিহাস
২tenantsbilling_rate_cards / billing_statements / billing_adjustments1:Mtenant_idএক FI-র দাম, বিল ও সংশোধন
৩usage_eventsbilling_statement_lines (USAGE)M:1 (উদ্ভূত)মাস শেষের গণনা quantity-তে লেখা — FK বা junction টেবিল নেইএক (FI, meter, মাস)-এর অনেক billable row এক লাইনের quantity হয়ে যায়
৪billing_rate_cardsbilling_statements1:Mcomposite FK (rate_card_id, tenant_id)এক card অনেক মাসের বিলের দাম দেয় — কিন্তু শুধু নিজের FI-র
৫billing_periodsbilling_statements1:MFK periodমাসের status-ই তার সব statement-এর অবস্থা
৬billing_statementsbilling_statement_lines1:MFK, ON DELETE CASCADEবিল তার লাইনে ভাগ হয়; redraft লাইন নতুন করে লেখে
৭billing_adjustmentsbilling_statement_lines1:0..1FK + সব statement মিলিয়ে adjustment_id-তে partial UNIQUEএক adjustment জীবনে ঠিক এক লাইনেই বসে
৮billing_statementsbilling_adjustments1:0..Mcomposite FK (applied_statement_id, tenant_id), NULL = Pendingএক বিল শূন্য বা তার বেশি অপেক্ষমাণ সংশোধন নিষ্পত্তি করে
ইচ্ছাকৃতভাবে কোনো junction টেবিল নেই। Domain-এর একমাত্র many-to-many — কাঁচা ব্যবহার operation ↔ statement — বিলিংয়ের সময় গুনে মিটিয়ে ফেলা হয়, আর পরে প্রমাণ থাকে: raw extract-এর billable row-র যোগফল অবশ্যই statement-এর সংখ্যার সাথে হুবহু মিলবে।

সম্পূর্ণ উদাহরণ — ঢাকা ব্যাংক PLC, অক্টোবর ২০২৬

ঢাকা ব্যাংক PLC (tenant_id T-D — পড়ার সুবিধার জন্য ছোট id; আসল মান UUID) ১ অক্টোবর থেকে দামে যুক্ত হলো: প্রতি QR generation-এ BDT 0.25, প্রতি validation-এ BDT 0.10। অক্টোবরে প্ল্যাটফর্ম তাদের জন্য ৫টি QR বানাল (৩ static, ২ dynamic) আর ৫টি validation চালাল (৪টি নিশ্চিত verdict, ১টি পুরনো request)। সেপ্টেম্বরে ২টি validation ভুলভাবে বিল হয়েছিল, তাই অক্টোবরে finance একটি credit লিখল। নভেম্বরের জন্য দাম কমারও চুক্তি হলো।
