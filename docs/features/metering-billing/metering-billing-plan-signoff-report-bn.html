অংশ ১

এক নজরে (TL;DR)

  • যা বানানো হবে: ব্যবহার-ভিত্তিক বিলিং — প্রতিটি QR generation ও validation-এর জন্য BDT, প্রতি FI-র জন্য একটি মাসিক statement (ঢাকা সময়ের ক্যালেন্ডার মাস)।
  • ডাটাবেসে যেভাবে নামছে: ৩টি এলাকা, ৭টি নতুন টেবিল — outbox_messages, usage_events এবং পাঁচটি billing_* টেবিল। SQL migration 010–012 ইতিমধ্যে লেখা ও দুবার চালিয়ে পরীক্ষিত; application code এখনো নেই।
  • পাইপলাইন: প্রতিটি QR operation একই transaction-এ একটি event row লেখে (outbox) → dispatcher সেটা একবার, চিরস্থায়ীভাবে usage খাতায় লেখে → মাস শেষে Billing বিলযোগ্য row গুনে rate card-এর দামে statement বানায়, adjustment যোগ/বিয়োগ করে।
  • টাকার নিরাপত্তা DB-তেই, শুধু code-এর ভরসায় নয়: numeric (কখনোই float নয়), composite FK — যাতে এক FI-র জিনিস অন্য FI-র বিলে ঢুকতে না পারে, আর trigger — যা usage অপরিবর্তনীয় রাখে এবং চূড়ান্ত মাসের বিল চিরকাল অপরিবর্তিত রাখে।
  • অনুমোদনে যা ঢাকা পড়ছে: এই schema ও module কাঠামো, এতে বসানো বিলিং নিয়ম, আর দুই ধরনের রিপোর্ট — যাতে implementation (১৫টি user story, ৭টি ticket) শুরু করা যায়।

অংশ ২

নির্বাহী সারসংক্ষেপ

প্রতিষ্ঠান (FI) ব্যবহারের জন্যই টাকা দেবে: প্ল্যাটফর্ম যে QR তার জন্য তৈরি করে ও যে QR তার জন্য যাচাই করে। মাস শেষে প্রতিটি বিলযোগ্য FI-র জন্য একটি statement তৈরি হয়, billing টিম দেখে মাসটি finalize করে, আর চূড়ান্ত statement আর কখনো বদলায় না — ভুল হলে পরের statement-এ adjustment দিয়ে শোধরানো হয়। Finance অনুমোদিত statement থেকে invoice দেয়; প্ল্যাটফর্ম statement দেয়, tax invoice নয়।

PRD — draft, sign-off বাকি টেকনিক্যাল ডিজাইন — v1.1 চূড়ান্ত DB migration 010–012 — লেখা ও পরীক্ষিত Application code — শুরু হয়নি ১৫টি user story · ৭টি ticket প্রস্তুত

ডিজাইনে বসানো ব্যবসায়িক নিয়ম

নিয়মসিদ্ধান্তDB কোথায় রক্ষা করে
কী চার্জ হবেপ্রতিটি সম্পন্ন generation; নিশ্চিত (conclusive) verdict-এর প্রতিটি validation — valid হোক বা না হোক। Protocol rejection (পুরনো / replay request) রেকর্ড হয় কিন্তু কখনো চার্জ হয় না।usage_events.billable লেখার সময়ই ঠিক; shape CHECK
কে টাকা দেবেযে FI কাজটি চেয়েছে। Validation-এর বেলায় যাচাইকারী FI, QR-দাতা নয় (ADR 0002)।usage_events.tenant_id
কে বিলযোগ্যযে FI-র ওই মাসে কার্যকর rate card আছে। Rate card না থাকলে (যেমন pilot/UAT) ব্যবহার রেকর্ড হয়, চার্জ হয় না।Rate card খোঁজা হয়; statement row-ই তৈরি হয় না
দামপ্রতি ইউনিট, প্রতি FI, BDT, ভবিষ্যৎ মাসের ১ তারিখ থেকে কার্যকর। কার্যকর হওয়ার পর দাম বদলায় না — নতুন দাম মানে নতুন row।UNIQUE(tenant_id, effective_from); UPDATE trigger-এ নিষিদ্ধ
মাসঢাকা সময়ের ক্যালেন্ডার মাস; কাজটি যে মাসে ঘটেছে সেই মাসের বিলে যায়, পরে রেকর্ড হলেও।occurred_at; billing_periods-এর PK YYYY-MM
চূড়ান্ততাUsage সম্পূর্ণ হলে স্বয়ংক্রিয় Draft; একজন নাম নথি operator পুরো মাস একসাথে finalize করেন, যা review হয়েছে ঠিক তাই। এরপর কিছুই বদলায় না।চূড়ান্ত মাসে সব লেখা trigger-এ বন্ধ; finalized_by/at বাধ্যতামূলক
সংশোধনশুধু adjustment: অঙ্ক ≠ 0, কারণ বাধ্যতামূলক, অপরিবর্তনীয়; একটি adjustment ঠিক একটি ভবিষ্যৎ statement-এ বসে।সব বিল মিলিয়ে UNIQUE(adjustment_id); composite FK একই FI-তে রাখে
টাকার হিসাবপ্রতি লাইনে একবার rounding, ২ দশমিক; মোট = rounded লাইনের যোগফল।অঙ্ক numeric(18,2), দাম numeric(18,4)

DDD শব্দ → ডাটাবেস শব্দ

ফিচারটি DDD দিয়ে পরিকল্পনা করা হয়েছে। Review-র সুবিধার জন্য প্রতিটি DDD ধারণার সরাসরি ডাটাবেস রূপ এখানে:

প্ল্যানে ব্যবহৃত DDD শব্দডাটাবেসে এর রূপ
Bounded context / সাব-ডোমেইনটেবিল-মালিকানার সীমানা। কোনো FK module-এর সীমানা পার করে না (design ৪.১, ADR 0001) — module-এর বাইরে শুধু id reference।
Aggregate (BillingPeriod)Transaction ও lock-এর সীমানা: একটি billing_periods row finalize হলে তার সব statement, line ও adjustment এক transaction-এ বদলায় (FOR SHARE lock)।
Integration eventএকটি outbox_messages row, producer-এর নিজের transaction-এর ভেতরে লেখা (অন্তত একবার পৌঁছায়)।
Domain invariantCHECK, UNIQUE, composite FK বা trigger — যেমন চূড়ান্ত মাসের অপরিবর্তনীয়তা trigger রক্ষা করে, কনভেনশন নয়।
Value objectলেখার সময় একবার কপি হয়ে আর বদলায় না এমন column — যেমন statement-এ দামের কপি।

অংশ ৩

সাব-ডোমেইন

চারটি bounded context জড়িত। প্রথম দুটি আজকের code-এ আছে; Metering ও Billing — এই প্ল্যানে নতুন যোগ হচ্ছে। পাঁচম একটি ভাগাভাগি-করা জিনিস — Outbox টেবিল — সব module-এর ব্যবহারের infrastructure, কোনো সাব-ডোমেইন নয়।

QrGeneration code-এ আছে

FI-র অনুরোধে BanglaQR P2P QR (static / dynamic) তৈরি করে, FI-র key দিয়ে sign করে, আর প্রতিটি সফল তৈরির রেকর্ড রাখে।

  • Spec অনুযায়ী static ও dynamic QR; শুধু tenant Active ও signing key ACTIVE হলে।
  • ডুপ্লিকেট সুরক্ষা: একই idempotency key ⇒ 409।
  • প্রতি সফলতায় এক row (tenant, type, key version) — QR string নিজে কখনো জমা থাকে না।
  • QrGenerated event প্রকাশ করে (design-এ ঠিক; code-এ এখনো নেই)।
যার ওপর নির্ভর করেTenancy (অনুমতি) · KeyCustody (signing key) যারা এর ওপর নির্ভর করেMetering (QrGenerated গ্রহণ করে) নিজের টেবিলqr_generations (বিদ্যমান)

QrVerification code-ে আছে

FI-র পাঠানো QR payload যাচাই করে (TLV/CRC গঠন, Bangladesh Bank trust store থেকে public key দিয়ে Ed25519 signature) verdict দেয়; প্রতিটি যাচাইয়ের এক row, যাচাইকারী FI-র নামে।

  • Verdict-এর মালিক: VALID, INVALID_SIGNATURE, KEY_NOT_FOUND, REQUEST_STALE …
  • Replay window ±৫ মিনিট; request id একবারই চলে।
  • QrValidated event প্রকাশ করে (design-এ ঠিক; code-এ এখনো নেই)।
  • শুধু business fact জানায় — কী billable, তা জানে না।
যার ওপর নির্ভর করেTenancy · InstitutionTrust (BB key directory) · KeyCustody · QrGeneration-এর সাথে ভাগাভাগি QR codec (Shared Kernel) যারা এর ওপর নির্ভর করেMetering (QrValidated গ্রহণ করে) নিজের টেবিলqr_validations (বিদ্যমান)

Metering নতুন — migration 011

প্রতিটি QR operation ঠিক একবার, চিরস্থায়ীভাবে গোনে, লেখার সময়েই বিলযোগ্যতা ঠিক করে, আর ব্যবহার প্রদানকারী FI-র নামে লেখে। "কী ব্যবহার হয়েছে" — এর একমাত্র সত্যের উৎস।

  • প্রতি operation-এ একটি অপরিবর্তনীয় row; ডুপ্লিকেট আসলে UNIQUE(source_type, source_id) বাদ দেয়।
  • বিলযোগ্যতা নীতি: নিশ্চিত verdict ⇒ billable; protocol rejection ⇒ নয় (ADR 0002)।
  • occurred_at বিলিং মাস ঠিক করে — কখন এসেছে তা নয়।
  • সংখ্যা, ভাগ (দিন / meter / verdict / tenant), raw extract ও usage completeness-এর উত্তর দেয়। Retention ≥ ১৩ মাস।
যার ওপর নির্ভর করেQrGeneration + QrVerification (Outbox দিয়ে event) · Tenancy (পরিচয়) যারা এর ওপর নির্ভর করেBilling (in-process query IMeteringQueries দিয়ে সংখ্যা নেয়) · reporting নিজের টেবিলusage_events

Billing নতুন — migration 012

প্রতিটি মাসের বিলযোগ্য ব্যবহারকে প্রতি FI-র জন্য review-করা, চূড়ান্ত statement-এ পরিণত করে। চূড়ান্ত হওয়ার পর কিছুই বদলায় না; সংশোধন পরের statement-এর adjustment। FI ও platform রিপোর্ট বানায়।

  • Rate card: প্রতি FI-র ইউনিট-দাম, ভবিষ্যৎ মাসের ১ তারিখ থেকে কার্যকর; append-only।
  • মাসের জীবনচক্র Open → Draft → Finalized; usage completeness ও finalize-র সময় expectedTotal পুনঃযাচাই।
  • Rating: সংখ্যা × দাম, প্রতি লাইনে একবার rounding; statement-এ ব্যবহৃত দামের কপি থাকে।
  • Adjustment (± credit/debit, কারণ বাধ্যতামূলক, অপরিবর্তনীয়, ঠিক একবার প্রয়োগ); ৩০ দিনের dispute window।
  • টাকা-সংক্রান্ত প্রতিটি write audit হয় (কে, কী, আগে/পরে মোট)।
যার ওপর নির্ভর করেMetering (শুধু সংখ্যা — নিজে বিলযোগ্যতা বিচার করে না) · Tenancy যারা এর ওপর নির্ভর করেভবিষ্যৎ Notification module (F8) · Finance সিস্টেমের বাইরে statement গ্রহণ করে নিজের টেবিলbilling_rate_cards · billing_periods · billing_statements · billing_statement_lines · billing_adjustments

অংশ ৪

ডাটাবেস স্কিমা ও নমুনা ডেটা

তিনটি domain, সাতটি টেবিল — সবই rvl-secure-bqr-manager · ডাটাবেস sbqr_app · schema public-এ। নিচে প্রতিটি টেবিলের সম্পূর্ণ column তালিকা, রক্ষাকারী নিয়ম, আর একই গল্পের নমুনা row — যাতে প্রতিটি id টেবিল থেকে টেবিলে খুঁজে মেলানো যায়। রীতি: UUID v7 PK application দেয়; সময় timestamptz (UTC); টাকা numeric — কখনোই float নয়।

QR MODULE (আছে)          OUTBOX (নতুন, ভাগাভাগি)        METERING (নতুন)                   BILLING (নতুন)
=================        ==========================      ================                  ==============

                 |  একই DB transaction              dispatcher, at-least-once        মাস শেষে গণনা, শুধু billable row

                                                                                                               =  billing_statements
                                                                                                               +- billing_adjustments  (credit / debit)

অংশ ৮

যে অনুমোদন চাওয়া হচ্ছে

এই প্ল্যানের অনুমোদন — constraint ও trigger-সহ তিন-domain, সাত-টেবিলের schema, তার চারপাশের module সীমানা, আর ওপরের রিপোর্ট ফরম্যাট — যাতে rvl-secure-bqr-manager-এ ১৫টি user story (৭টি build ticket)-এর implementation শুরু করা যায়।

যেসব বিষয়ে আপনার মত বিশেষভাবে চাওয়া হচ্ছে

  • Schema ও নিশ্চয়তা — trigger-এ রক্ষিত অপরিবর্তনীয়তা, একই-FI composite FK এবং মাস-স্তরের finalization মডেল কি production ডিজাইন হিসেবে টেকে?
  • Invalid outcome-এও চার্জ (নিশ্চিত verdict হলে QR খারাপ হলেও বিল) — commercial নিশ্চিতকরণ PRD Q3।
  • Static = dynamic দাম, আলাদা meter ও আলাদা লাইনে দেখানো — Product-এর সাথে যৌথ নিশ্চিতকরণ দরকার (C15 / PRD Q9)।
