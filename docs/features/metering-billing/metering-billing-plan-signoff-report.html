Usage Metering & Billing — Implementation Plan

Per-use charging for QR generation and validation: monthly statements per financial institution, finalised months that never change, and corrections only by adjustment. This report presents the plan for Head-of-Engineering approval, translated into database terms.

Date: 01 Oct 2026 Target: rvl-secure-bqr-manager · PostgreSQL 16 Audience: Head of Engineering Design v1.1 · migrations 010–012

Section 1

TL;DR

  • What we will build: usage-based billing — BDT per QR generation and per QR validation, one monthly statement per financial institution (FI), Dhaka calendar month.
  • How it lands in the database: 3 new areas, 7 new tables — outbox_messages, usage_events, and five billing_* tables. SQL migrations 010–012 are already written and double-run tested; no application code exists yet.
  • The pipeline: every QR operation writes an event row in the same transaction (outbox) → a dispatcher records it once in an append-only usage ledger → at month end Billing counts billable rows × rate-card prices into statements, plus/minus adjustments.
  • Money is protected in the DB, not just in code: numeric (never float), composite foreign keys that stop one FI's data crossing into another FI's bill, triggers that make usage append-only and finalised statements immutable.
  • Approval covers: this schema and module structure, the billing rules encoded in it, and the two report formats — so implementation (15 user stories, 7 tickets) can start.

Section 2

Executive summary

Institutions pay only for what they use: each QR the platform creates for them and each QR the platform checks for them. At month end the platform prepares one statement per paying FI, the billing team reviews and finalises the month, and finalised statements never change — a mistake is corrected by an adjustment on a later statement. Finance invoices from the approved statements; the platform produces statements, not tax invoices.

Section 3

Sub-domains

Four bounded contexts are involved. The first two exist in code today; Metering and Billing are the new ones this plan adds. A fifth shared piece — the Outbox table — is infrastructure all modules use, not a sub-domain.

QrGeneration exists in code

Creates BanglaQR P2P QR codes (static / dynamic) for FIs, signed with the FI's key, and records every successful creation.

  • Create static & dynamic QRs per spec; only when the tenant is Active and its signing key ACTIVE.
  • Duplicate protection: same idempotency key ⇒ 409.
  • One row per success (tenant, type, key version) — the QR string itself is never stored.
  • Publishes QrGenerated (designed; not yet wired).
Depends onTenancy (admission) · KeyCustody (signing keys) Dependent sub-domainsMetering (consumes QrGenerated) Tables ownedqr_generations (existing)

QrVerification exists in code

Verifies FI-submitted QR payloads (TLV/CRC structure, Ed25519 signature via the Bangladesh Bank trust store) and returns a verdict; one row per check, in the verifying FI's name.

  • Owns the verdict vocabulary: VALID, INVALID_SIGNATURE, KEY_NOT_FOUND, REQUEST_STALE …
  • Replay window ±5 min; request id single-use.
  • Publishes QrValidated (designed; not yet wired).
  • States business facts only — it does not know what is billable.
Depends onTenancy · InstitutionTrust (BB key directory) · KeyCustody · shared QR codec with QrGeneration (Shared Kernel) Dependent sub-domainsMetering (consumes QrValidated) Tables ownedqr_validations (existing)

Metering new — migration 011

Counts every QR operation exactly once, permanently, decides billability at write time, and attributes usage to the paying FI. The single source of truth for "what was used".

  • One immutable row per operation; duplicates collapse via UNIQUE(source_type, source_id).
  • Billability policy: conclusive verdict ⇒ billable; protocol rejection ⇒ not (ADR 0002).
  • occurred_at fixes the billing month, regardless of arrival time.
  • Serves counts, breakdowns (day / meter / verdict / tenant), raw extracts, and usage-completeness answers. Retention ≥ 13 months.
Depends onQrGeneration + QrVerification (events via Outbox) · Tenancy (identity) Dependent sub-domainsBilling (pulls counts via in-process query IMeteringQueries) · reporting Tables ownedusage_events

Billing new — migration 012

Turns each month's billable usage into reviewed, finalised statements per FI. After finalisation nothing changes; corrections are adjustments on a later statement. Produces the FI and platform reports.

  • Rate cards: per-FI unit prices, effective from a future month's 1st; append-only.
  • Month lifecycle Open → Draft → Finalized, gated by usage completeness and an expectedTotal re-check at finalise.
  • Rating: quantity × price, rounded once per line; statement keeps a copy of the rates used.
  • Adjustments (± credit/debit, mandatory reason, immutable, applied exactly once); 30-day dispute window.
  • Every money write is audited (who, what, totals before/after).
Depends onMetering (counts only — never re-judges billability) · Tenancy Dependent sub-domainsfuture Notification module (F8) · Finance consumes statements outside the system Tables ownedbilling_rate_cards · billing_periods · billing_statements · billing_statement_lines · billing_adjustments

4.1 · Outbox — outbox_messages shared infrastructure

The reliability hinge: the QR module writes its "QR happened" event inside the same transaction as the QR row itself, so a committed QR can never silently lose its news. A dispatcher later delivers each event to Metering, retrying with backoff; PROCESSED rows are purged after 7 days.

4.3 · Billing — five tables new

Think of a paper utility bill. Each table answers one question: the price list (what a unit costs, from when), the month register (is this month draft or final), the statement (one FI's total for the month), its lines (how the total breaks down), and adjustments (hand-applied credits/debits). A statement has no status column of its own — the month's row is the single status for all its statements, so a whole month is drafted and finalised atomically.

TableAnswersIf it were missing…
billing_rate_cardsWhat does a unit cost for this FI, from which month?Old months would be silently re-priced whenever prices change
billing_periodsIs this month Draft or Finalized?"Finalise all FIs at once" and "two people calculating at once" become hard to stop
billing_statementsWhat is one FI's total for the month?No per-FI bill exists at all
billing_statement_linesHow did that total arise?The FI cannot see what it is paying for
billing_adjustmentsWhich credit/debit lands on which bill?Finalised bills could never be corrected

What finalising October does (one transaction)

  1. Ops confirms the reviewed grand total 0.50 + 0.98 = 1.48 (expectedTotal); a fresh recalculation that disagrees stops the finalise with 409 DRAFT_CHANGED.
  2. adj-1.applied_statement_id ← st-1 (both are T-A, so the composite FK accepts it).
  3. billing_periods['2026-10'].status ← FINALIZED — one row change finalises st-1, st-2 and all their lines.
  4. An audit row billing.period.finalized is written. Order matters: adjustments first, month second. After the month flips, any further write to October's bills is rejected by trigger.

Section 5

Table relationships

Solid guarantees live inside Billing as real foreign keys. Cross-module links are id references only — by design, no FK ever crosses a module boundary (ADR 0001), which is what keeps the modules independently deployable and the schemas loosely coupled.

The only many-to-many in the domain — raw usage operations ↔ statements — never becomes a junction table. It is resolved by aggregation at billing time: all billable rows of one (FI, meter, month) collapse into a single USAGE line's quantity. Every quantity remains provable afterwards via the raw usage extract, whose billable rows must sum exactly to the statement.
