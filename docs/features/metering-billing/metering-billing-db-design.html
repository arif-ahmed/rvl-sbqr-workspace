Section 2

Tables — purpose and columns

usage_events — the usage ledger Metering

Every QR generation and validation the platform performs becomes exactly one row here, attributed to the FI that asked for the work. This table is the only source of "what was used": billing counts it, reports read it, disputes are proven with it. Rows are written once and never change, giving an auditable usage history.

ColumnTypePurpose
usage_event_iduuidPK
tenant_iduuidThe FI whose bill this counts towards (requester / verifying FI)
meter_codevarchar(40)GENERATION_STATIC / GENERATION_DYNAMIC / VALIDATION
billablebooleanFixed at write time: conclusive verdict ⇒ true, protocol rejection ⇒ false
detailvarchar(40)Verdict for validations, NULL for generations
source_type / source_idvarchar(30) / uuidWhich QR operation — together UNIQUE (exact-once counting)
source_event_iduuidWhich outbox event produced it (tracing only)
client_referencevarchar(100)The FI's own idempotency key / request id
occurred_at / recorded_attimestamptzWhen it happened (fixes the billing month) / when it was recorded

billing_rate_cards — the price list Billing

Prices per FI, per unit, taking effect on a future month's 1st. Because rows are append-only and looked up by month, a price rise or cut can never silently rewrite a past or running month — the new row simply takes over from its effective_from. An FI with no card in force for a month is recorded but never charged.

ColumnTypePurpose
rate_card_iduuidPK
tenant_iduuidWhich FI (UNIQUE with effective_from)
effective_fromdateFirst month it applies to — always the 1st, always a future month
generation_rate / validation_ratenumeric(18,4)BDT per QR created / per validation
currency / created_by / created_atchar(3) / auditBDT; who entered the price and when

billing_periods — the month register Billing

One row per Dhaka calendar month. Statements carry no status of their own: the whole month is drafted, recalculated and finalised together, and "October is final" lives in exactly one place. The row is locked during recalculate/finalise, which also serialises concurrent runs.

ColumnTypePurpose
periodchar(7)PK — YYYY-MM
statusvarchar(15)DRAFT → FINALIZED; drives the immutability triggers of the whole month
drafted_attimestamptzWhen the month was auto-drafted (after month end + grace + usage completeness)
finalized_at / finalized_bytimestamptz / varcharWho approved the month and when — mandatory once finalised

billing_statements — one FI's monthly bill Billing

One row per billable FI per month. It keeps a copy of the rates used at billing time, plus the roll-up of its lines. A negative total is a valid state (a credit), not an error.

ColumnTypePurpose
statement_iduuidPK
tenant_id + perioduuid + char(7)Which FI, which month — UNIQUE together (one bill per FI per month); FK → periods
rate_card_iduuidFK (composite with tenant_id) → the rate card used — same FI only
generation_rate / validation_ratenumeric(18,4)Copies of the prices used; later price changes never reach this bill
subtotal / adjustments_total / totalnumeric(18,2)USAGE lines / ADJUSTMENT lines / their sum
currency / calculated_atchar(3) / timestamptzBDT; last calculation time

billing_statement_lines — how the total arises Billing

The itemised body of the bill: one USAGE line per meter (so an FI sees static, dynamic and validation counts separately) and one line per applied adjustment. Lines are never updated — a recalculate deletes and rewrites them all, which keeps a draft month always consistent with the ledger.

ColumnTypePurpose
statement_id + line_nouuid + intComposite PK; FK → statements (ON DELETE CASCADE)
line_typevarchar(15)USAGE or ADJUSTMENT
meter_codevarchar(40)USAGE: which meter (one line per meter per bill)
adjustment_iduuidADJUSTMENT: FK → adjustments, unique across all bills
descriptionvarchar(200)Text printed on the bill
quantity / unit_rate / amountbigint / numeric(18,4) / numeric(18,2)Count × price, rounded once per line

billing_adjustments — credits & debits Billing

The only way to correct a finalised bill: an immutable, reason-carrying amount that waits as Pending and settles on exactly one future statement when that month is finalised. A wrong adjustment is reversed by an opposite one — the audit trail never has a hole.

ColumnTypePurpose
adjustment_iduuidPK
tenant_iduuidWhich FI
amountnumeric(18,2)+ debit / − credit, never 0
reasonvarchar(500)Mandatory written reason
created_by / created_atauditWho recorded it, when
applied_statement_iduuidNULL = Pending; set once (composite FK, same FI) when that statement's month is finalised

Section 3

Relationships

All hard guarantees live inside Billing as real foreign keys. Links into usage_events and tenants are id references by design — no FK crosses a module boundary, so Metering and Tenancy can evolve without re-locking Billing's schema.

#FromToCardinalityEnforced byBusiness meaning
1tenantsusage_events1:Mtenant_id (no FK)An FI's usage history
2tenantsbilling_rate_cards / billing_statements / billing_adjustments1:Mtenant_idAn FI's prices, bills and corrections
3usage_eventsbilling_statement_lines (USAGE)M:1 derivedMonth-end count written into quantity — no FK, no junction tableMany billable rows of one (FI, meter, month) collapse into one line's quantity
4billing_rate_cardsbilling_statements1:Mcomposite FK (rate_card_id, tenant_id)A card prices many monthly bills — but only its own FI's
5billing_periodsbilling_statements1:MFK periodThe month's status is the status of all its statements
6billing_statementsbilling_statement_lines1:MFK, ON DELETE CASCADEA bill is itemised by its lines; redraft rewrites them
7billing_adjustmentsbilling_statement_lines1:0..1FK + partial UNIQUE on adjustment_id across all statementsAn adjustment lands on exactly one line, ever
8billing_statementsbilling_adjustments1:0..Mcomposite FK (applied_statement_id, tenant_id), NULL = PendingA bill settles zero or more waiting corrections
There is deliberately no junction table. The only many-to-many in the domain — raw usage operations ↔ statements — is resolved by aggregation at billing time, and stays provable afterwards: the billable rows of the raw extract must sum exactly to each statement's quantities.

Section 5

Worked scenario — Dhaka Bank PLC, October 2026

Dhaka Bank PLC (tenant_id T-D — short id for readability; real values are UUIDs) signed up with prices from 1 October: BDT 0.25 per QR generation, BDT 0.10 per validation. During October the platform created 5 QRs for them (3 static, 2 dynamic) and ran 5 validations (4 with conclusive verdicts, 1 stale request). Back in September, 2 validations had been wrongly charged, so finance recorded a credit in October. A price cut was also agreed for November.

6 · How the database produced that bill

  1. Month closes: billing_periods['2026-10'] is created DRAFT — only after October ended, the grace window passed and Metering confirmed all October usage has arrived.
  2. Who is billable: Dhaka Bank has a rate card in force for October (rc-4) ⇒ statement st-3 is created, and rc-4's rates are copied onto it.
  3. Counting: billable October rows for T-D are grouped by meter — 3 static, 2 dynamic, 4 validations (each 4 × 0.10 = 0.40, rounded once per line) — and written as USAGE lines. ue-105 joins October via occurred_at; ue-110 is skipped via billable = false.
  4. Corrections: the Pending credit adj-2 becomes line 4 (−0.20).
  5. Totals: 0.75 + 0.50 + 0.40 = 1.65; 1.65 − 0.20 = BDT 1.45.
  6. Finalisation (one transaction): ops confirms the reviewed total 1.45 (expectedTotal); adj-2.applied_statement_id ← st-3; the month flips to FINALIZED. From that moment triggers refuse any write to October's statements, lines or adjustments — the September mistake stays corrected via the credit, and the audit trail stays intact.
  7. November: rc-5 prices take over (0.20/generation); October's st-3 still shows 0.25 because it holds its own copy.
