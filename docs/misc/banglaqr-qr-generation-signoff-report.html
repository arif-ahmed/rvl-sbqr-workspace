BanglaQR P2P — Payload Generation & Signing

A build-vs-requirement walkthrough for the Ed25519 QR issuance flow, prepared for Head of Engineering sign-off ahead of the 10 Sep feature freeze.

Module: QrGeneration + KeyCustody + IdentityAccess Source of truth: BB BanglaQR P2P spec, §2 Prepared 10 Sep 2026

Executive summary

TL;DR

✓ Requirement met — with one scope note Server-to-server issuance is live; direct mobile-app calling is deferred by design.
  • Static and dynamic QR issuance are two explicit endpoints, each behind OAuth2 client-credentials with a dedicated qr:generate scope — nothing is issuable anonymously.
  • Signing uses Ed25519 exactly as specified; the private key never leaves the KeyCustody module — QrGeneration only ever receives 64 signature bytes back.
  • Every payload field keeps the spec's EMVCo Tag semantics 1:1 — amount (Tag 54) is carried as a string end-to-end, never parsed to a number, so the signed bytes can never silently drift from the displayed amount.
  • Bad input, an inactive signing key, a signing failure, or anything unexpected all reject the request — there is no fallback or partial-payload path — and each rejects with its own stable code, incl. a dedicated SIGNING_FAILED (added since the last draft) that's no longer indistinguishable from a generic software bug.
  • Every rejection is now traceable: a shared correlationId ties the caller-facing error, the log line, and an audit row together — including paths (idempotency conflict, unexpected DB error) that previously left no audit trail.
  • Gap to flag: the spec describes the Recipient FI's mobile app calling the endpoint directly via SDK; today's caller is the FI's backend (server-to-server). Mobile-facing SDK wiring is tracked post-freeze — see Open items.

As written, unedited

Feature requirement — verbatim

Kept word-for-word from the requirement note, so this report is checkable line-by-line against the same text the build was scoped from.

📄 Bangla QR Payload Generation and Signing

The Recipient Financial Institution's mobile application will integrate the provided SDK and use the assigned credentials to securely call the platform's QR generation endpoint with the required recipient and transaction information.

Upon receiving the request, the platform will validate the request and construct the QR payload in accordance with the Bangla QR specification and the applicable EMVCo TLV format. Depending on the request, the service will generate either a static or dynamic QR payload.

The platform will digitally sign the required QR payload information using the Ed25519 digital signature algorithm and the Recipient Financial Institution's private key stored securely in the platform's Private Key Vault. The generated digital signature will be incorporated into the QR payload in accordance with the Bangla QR specification. The corresponding public key maintained in the Bangladesh Bank Trust Store can subsequently be used by the Sender/Payer Financial Institution to verify the authenticity and integrity of the QR payload.

After successfully constructing and signing the payload, the service will return the generated QR data to the Recipient Financial Institution's application. The application can then render the QR code for display, download, or sharing with the intended sender/payer.

If the request contains invalid or incomplete information, if the required private key is unavailable, or if the signing operation fails, the QR generation request will be rejected with an appropriate error response.

Mental model

How it actually works

One request, five hops. Nothing about the private key ever crosses a module boundary — only signature bytes do.

FI backend gets a token

Client credentials exchanged at the token endpoint for a short-lived bearer token scoped to qr:generate.

IdentityAccess
Request validated & tenant resolved

Recipient name/city/PAN and (for dynamic) amount are checked field-by-field; the caller's tenant is pinned from the token, not the request body.

QrGeneration
TLV payload constructed

Fields are written into EMVCo tags in spec order — everything up to the signature block.

QrGeneration
Payload signed, never the key exposed

QrGeneration asks KeyCustody for a signature over the built bytes. KeyCustody checks the tenant's key is ACTIVE, signs with Ed25519, and returns only signature bytes.

KeyCustody
Finalized, audited, returned

Signature tags + CRC are appended, an audit line is written (metadata only — the raw payload itself is never persisted), and the signed QR string goes back to the caller.

Audit · QrGeneration
Same flow, at the code-component level

Two concrete chains, no {Static|Dynamic} placeholders. Both forward through one shared QrIssuancePipeline (no duplicated business logic) and thread a single correlationId, minted at the top of the pipeline, through every branch — a rejection, a signing failure, and a success all leave a trace under the same value. Contract

The APIs, one case at a time

1 · Obtain an access token

Every downstream call needs this first. The scope granted here is what actually gates access to QR issuance — without qr:generate on the token, the generation endpoints refuse the request regardless of who's calling.

POST /v1/oauth/token anonymous — client_secret is the credential

Client-credentials grant. Rate-limited per IP to blunt credential-stuffing against this exact endpoint.

Request
{
  "grant_type": "client_credentials",
  "client_id": "fi-dutchbangla-001",
  "client_secret": "••••••••••••••••"
}
Response · 200
{
  "access_token": "eyJhbGciOiJIUzI1NiJ9...",
  "token_type": "Bearer",
  "expires_in": 900,
  "scope": "qr:generate qr:validate"
}
Why the scope matters here: a tenant FI's token is issued only qr:generate / qr:validate plus a bound tenant_id claim — never admin. Admin-level tokens are a structurally separate bootstrap credential. This is what stops one tenant's leaked credential from ever reaching another tenant's data or the admin surface.

2 · Generate a static QR (no amount)

POST /v1/qr/generate/static scope: qr:generate

Recipient displays this once and reuses it for any sender/amount. Rejected with 400 if a transactionAmount is supplied — static means no amount, by construction.

How the caller turns this into a QR code
  1. The 201 response hands back qrPayload as-is — plain text, never an image. The platform's job stops at producing this signed string.
  2. The FI's app (web, mobile, or POS) passes that exact string into any standard QR-image encoder (e.g. ZXing, qrcode.js) — the same library any EMVCo-compliant merchant QR uses — to rasterize a scannable PNG/SVG.
  3. The app displays it on-screen, offers it as a download, or shares it — the three outcomes the requirement names — using payloadHash only for its own audit/receipt correlation, never re-parsing the payload itself.
  4. Trust doesn't depend on the rendering step: Tags 80/81 are already fixed into the string before it left the platform, so any tampering after this point — including a buggy re-encode — breaks the Ed25519 check at verify time, not before.

Fail-closed by design

What rejection looks like

No stack traces, no partial payloads. Every rejection is a small, stable JSON body — plus, as of this revision, every one of them also writes an audit line under a shared correlationId, so a support ticket can be traced from the caller's error message straight back to the exact log line and audit row.

Why split SIGNING_FAILED from GENERATION_FAILED: the first is a key/HSM-layer problem KeyCustody surfaces on purpose; the second is a catch-all for anything unforeseen. Same HTTP status, different code — an on-call engineer scanning logs no longer has to open the code to tell which one just fired.
⚠ TENANT_NOT_ACTIVE is currently mis-mapped: QrIssuancePipeline rejects with ErrorCode.Forbidden, but the controller's error switch has no arm for it, so it falls to the generic 500 GENERATION_FAILED path instead of a distinct 403. The audit line is still correct and complete either way — only the response the caller sees is affected.

Why these field names

Payload naming, traced to the spec

Every DTO property name was chosen to read as the obvious English name for its EMVCo tag — never a raw tagNN — so the code stays self-documenting against the spec table it implements.

transactionAmount
Tag 54
Kept as a string, never double/float, and never reformatted between sign and verify. Security constraint A8 — amount fidelity: reformatting "100.50" → "100.5" silently changes the signed bytes.
recipientPan
Tag 26 · sub 03
"PAN" (Primary Account/wallet Number) is the spec's own term for the recipient identifier under the merchant account info template — matching it avoids inventing a synonym the spec doesn't use.
recipientName / recipientCity / postalCode
Tags 59 / 60 / 61
Named directly after the spec's field titles (Table 3A) — a reader can diff the DTO against the spec table with no translation step.
customerLabel / purposeOfTransaction
Tag 62 · sub 06 / 08
Both live under the spec's "Additional Data Field Template" — named per their sub-tag titles rather than a generic metadata bag, so validation rules (length caps) stay attached to the right field.
signatureKeyVersion
n/a — response only
Surfaces which key version signed the payload without exposing the internal logical key id — enough for audit correlation, nothing an attacker could use to target a specific key record.

Who does what

Component responsibilities

FI backend (caller)

Holds tenant credentials, calls the token endpoint, then the generation endpoint. Renders/shares the returned QR.

IdentityAccess

Issues scoped bearer tokens, hashes/verifies client secrets, keeps tenant admission state.

QrGeneration

Validates the request, builds the TLV payload, asks KeyCustody to sign, finalizes and returns the QR — never touches key material.

KeyCustody

Owns Ed25519 private keys end-to-end. Exposes a sign operation only — private bytes never leave this module.

InstitutionTrust

Publishes each tenant's public key so a sender/payer institution can later verify the signature.

Audit

Records who issued what, when, and the outcome — the tamper-evident trail this sign-off leans on.

For the record

Open items before this is fully "as specified"

Mobile SDK plane is not yet wired. The requirement describes the Recipient FI's mobile application integrating an SDK and calling this endpoint directly. Today, the endpoint is server-to-server only (client-credentials, no mobile/device auth path) — the mobile-facing surface is an explicitly deferred, post-freeze item. Recommend approving the server-side implementation now and tracking the SDK/mobile-auth plane as a separate, named follow-up rather than letting it slip in silently.
