BanglaQR P2P — Payload Verification

A build-vs-requirement walkthrough for the Ed25519 QR verification flow, prepared for Head of Engineering sign-off — companion to the QR Generation sign-off.

Module: Verification + InstitutionTrust + KeyCustody Source of truth: BB BanglaQR P2P spec, §2.5 / §3 Prepared 11 Sep 2026

Executive summary

TL;DR

✓ Core path matches spec — one external dependency open
  • One endpoint, POST /v1/qr/validate, behind a dedicated qr:validate OAuth2 scope. A rejected QR is still a 200 response — the verdict is the answer, not an error.
  • Pipeline, in order and fail-closed: replay window (± 5 min) → bounded TLV parse → CRC check → derive Institution ID → classify (P2P vs NON_P2P) → resolve the issuer's key from the single BB trust store (Annex B) → Ed25519 verify against the active key → historical-key retry against the latest RETIRED key. Every rejection carries a stable reason code and an audit line.
  • The key is never taken from the payload — only from the trust store (C16). Tenant-owned and external issuers both resolve through the same GetInstitutionPublicKeyQuery; there is no own-custody branch.
  • Temporal validity (C16) is enforced in the trust-store query itself: ValidFrom ≤ now, (ValidTo IS NULL OR ValidTo > now), RevokedAt IS NULL. An expired or revoked key with ACTIVE status is no longer returned.
  • Open item: the BB Trust Store is a mock today, seeded locally. No real BB contract exists yet, so a brand-new BB key is invisible until the data is published into the directory.

As written, unedited

Feature requirement — verbatim

📄 Bangla QR Payload Verification

The Sender Financial Institution's mobile application will integrate the provided SDK and use the assigned credentials to securely call the platform's QR verification endpoint with the QR payload.

Upon receiving the request, the platform will parse the QR payload in accordance with the Bangla QR specification and the applicable EMVCo TLV format. The service will validate the CRC to detect any corruption or alteration of the QR payload and derive the Recipient Financial Institution's Institution ID from the relevant TLV fields.

Using the derived Institution ID, the service will retrieve the corresponding public key from the platform's local trust store. If the public key is not available locally, the service will retrieve it from the Bangladesh Bank (BB) Trust Store. The public key will then be used to verify the QR payload's digital signature using the Ed25519 signature verification algorithm.

Based on the CRC and signature verification results, the service will return the verification response to the Sender Financial Institution. If the signature is invalid, or the required public key is unavailable or revoked, the QR payload will be considered invalid. Any subsequent transaction initiation or processing by the Sender Financial Institution is outside the scope of this platform.

Mental model

How it works

One request, seven gates. Each gate can end the request, each ending writes an audit line, and nothing is ever "assumed valid" — what isn't proven valid is rejected.

Authenticated request

Sender FI's backend submits the scanned payload with a requestId + timestamp, authenticated by a qr:validate-scoped token.

Replay window — ± 5 minutes

Timestamp too old or too far in the future → REQUEST_STALE. A reused request id is caught by a database unique constraint → REQUEST_REPLAYED.

Parse & CRC

Bounded TLV parse; CRC recomputed over the whole string before any field is trusted. Any corruption anywhere → STRUCTURAL_INVALID / CRC_MISMATCH.

Derive Institution ID, resolve key from the single BB trust store

Institution ID comes from the payload's Tag 26 sub 01 ‖ sub 02. The same GetInstitutionPublicKeyQuery resolves every issuer — tenant-owned or external. The query enforces C16 temporal validity on the way out (ValidFrom ≤ now, not expired, not revoked). A key carried inside the payload is never used.

Ed25519 verification (active key)

Signature (Tags 80+81, exactly 64 decoded bytes) checked against the same canonical bytes that were signed at issuance. Failure never bypasses — the next step is the only fall-through.

Historical-key retry (Phase 4)

If the active key doesn't verify, the latest RETIRED key is tried — a structurally valid QR issued before a recent rotation would otherwise fail forever. REVOKED keys are never retried (fail-closed on compromise). A hit is recorded as VALID with VERIFIED_HISTORICAL_KEY.

Verdict returned & audited

Verdict, trust source and payload hash go back with one audit line — success and failure both log, under a shared correlation id. The verifying tenant (from the bearer token, not the body) owns the audit row (C5).

        │   └─ publicKey = PEM → Ed25519PublicKeyParameters ← publicKeyPem

        └─ IAuditLogger.LogAsync() → AuditEntry

The handler is the whole story: everything from verifying-tenant resolution to the audit line happens inside ValidateQrCommandHandler.Handle. Key material crosses only one boundary, as a public PEM; the Ed25519 verify itself never sees a private key (C17). The trust-store resolver is the single authority — there is no own-custody branch and no live BB call.

Contract

The API

POST /v1/qr/validate scope: qr:validate

Caller first gets a client-credentials token (same token endpoint as issuance). The verdict is the answer: an invalid QR is a successful API call with an invalid verdict — that's why rejections here are 200, not 4xx.

Field notes: qrPayload is the raw scanned string, capped at 2048 bytes (validation + codec each enforce it). requestId / requestTimestamp drive C6 replay protection — both are optional on the wire: when a client omits them, the controller mints a fresh requestId (Guid.NewGuid().ToString("N")) and stamps DateTimeOffset.UtcNow. Clients that omit them lose the C6 replay-detection guarantee for their own traffic (every request looks like a brand-new one); when the on-the-wire C6 contract returns, callers should send both. Recipient fields appear only on VALID verdicts.

For the record

Open items

1 · BB Trust Store is a mock. Verification reads the seeded trust directory; no real BB contract is published yet. The local-read design is deliberate (a BB outage can't stall verification), but keep the real-BB integration on the GA dependency list.
Closed since the last revision: · Gate 1 (C16). Key expiry dates are now enforced inside GetInstitutionPublicKeyQueryHandler — ValidFrom ≤ now, (ValidTo IS NULL OR ValidTo > now), RevokedAt IS NULL. An expired or revoked key with ACTIVE status is no longer returned as an activator. · Historical-key resolution (Phase 4). A signature that misses the active key is retried against the latest RETIRED key; a hit is recorded as VALID · VERIFIED_HISTORICAL_KEY. REVOKED keys are never retried — fail-closed on compromise.
Also tracked: no rate-limit policy on /qr/validate yet (C7, due with the 22 Oct load-test milestone) · on-the-wire C6 contract (caller-supplied requestId + requestTimestamp) not yet enforced; today they're server-generated when omitted, so a client that doesn't send them loses the C6 replay-detection guarantee for its own traffic · mobile SDK plane deferred, same as issuance.
