Overview

What this document is for

We are a QR Issuance and Verification Service Provider: Financial Institutions (FIs) — banks, mobile financial services, payment companies — register with our platform so we can generate and check BanglaQR codes on their behalf, within the rules Bangladesh Bank sets for the network. Registration is not mandatory and is not automatic; only an FI that has registered with us can use the service. Institution Onboarding is the process by which our Platform-Admin team registers one: creating its tenant record, provisioning the API credentials it authenticates with, minting its Ed25519 signing key, and activating the tenant. This guide documents that process call by call — the payload each step needs, the response it returns, and exactly which field from that response feeds the next call — for QA exercising the flow in Postman and for operations staff who need to get the right value into the right field, in the right order, the first time.

Role

Who runs this flow

One role performs every call in this document: the Platform-Admin. It holds the platform's highest privilege — the only credential that can create, configure, and activate a tenant — and it authenticates with a bootstrap client credential held in configuration, not tied to any single institution. Every endpoint below except the token exchange itself requires this role's bearer token.

Platform-Admin

  • Registers each participating Financial Institution as a tenant on our platform.
  • Provisions the tenant's client_id / client_secret pair.
  • Mints or rotates the tenant's Ed25519 signing key in KeyCustody.
  • Moves the tenant through its lifecycle: Pending → Active → Suspended / Terminated.
Once this flow hands off the client_id / client_secret from step 3, the institution operates under its own tenant-scoped credential to request and verify QR codes — a separate role, separate flow, outside the scope of this document.

Onboarding flow

The full sequence, at a glance

The task brief names four calls — token, tenant-configuration, crypto-keys, activate — which assumes a tenant :id already exists. It doesn't yet at that point, so the actual chain has one call in front of it: registering the institution. That's what produces the :id every later call needs. A sixth call — registering the tenant's mobile-app allow-list — sits between the signing-key mint and the activate: a tenant whose mobile apps are not on this allow-list fails closed at the OAuth token endpoint with invalid_client / package_mismatch. All six are shown below in the order they must run.

1 Admin token POST /oauth/token → access_token
→
2 Register institution POST /admin/tenants → tenantId
→
3 Provision credentials POST …/tenant-configuration → clientId + clientSecret
→
4 Mint signing key POST /crypto-keys → key status: Active
→
5 Register mobile app(s) POST …/applications → appId (×N)
→
6 Activate tenant POST …/activate → status: Active
POST /v1/oauth/token
No auth required

Step 1 of 6. Exchanges the platform bootstrap client_id / client_secret (held in configuration, not tenant data) for a bearer token scoped admin. There is no separate login for a Platform-Admin — the client credential is the authentication, so this route is anonymous by design and is instead protected by a per-IP rate limiter. This same endpoint is reused later by the Institution-Admin, with the FI's own credentials, once step 3 has issued them.

POST /v1/admin/tenants
Platform-Admin bearer token

Step 2 of 6 — the prerequisite the task brief takes for granted: creates the tenant row itself, in status Pending. No client credential, no signing key, and no mobile-app allow-list row are created here on purpose; those are separate, dedicated calls (steps 3, 4 and 5) so each can be re-run, rotated, or audited independently.

POST /v1/admin/tenants/:id/tenant-configuration
Platform-Admin bearer token

Step 3 of 6. Mints the credential the FI will actually authenticate with: a client_id shaped {institutionCode}-{8hex}, and a 256-bit client_secret. No request body — the tenant is entirely identified by the route :id. Tenants in Pending or Active may be provisioned; Suspended or Terminated tenants are refused, and provisioning twice on an already-configured tenant is a conflict, not a silent overwrite.

POST /v1/crypto-keys
Platform-Admin bearer token

Step 4 of 6. Mints the tenant's first signing key — the private half never leaves KeyCustody (C17); this endpoint only ever returns the public half. Generate mode has the platform create a fresh Ed25519 keypair; Adopt mode lets the FI bring an existing key, provided its public half was already seeded into the trust store via /admin/institutions beforehand — the same Ed25519 key pair the BB BanglaQR P2P specification has each institution generate independently (openssl genpkey -algorithm Ed25519) and register with the Bangladesh Bank trust store as {institutionCode}-public.pem.

POST /v1/admin/tenants/:id/applications
Platform-Admin bearer token

Step 5 of 6. Registers the mobile-app identifier(s) the FI will ship — Android applicationId or iOS bundle ID — onto the tenant's allow-list. The OAuth token endpoint consults this list at mint time: a token request whose package_id claim is not on the list is rejected with invalid_client / package_mismatch, and a row that is later SUSPENDED rejects every device pinning it (the per-app kill switch). Call this endpoint once per (platform, package_id) the FI ships — typically two calls in practice (one Android, one iOS) for an FI that publishes the same app to both stores.

Repeat this call once per platform the FI ships. The same reverse-DNS string on ANDROID and IOS is legal — that's two rows. The same string twice on one platform is not: the DB unique index ix_tenant_applications_platform_package_id rejects the second insert with 409 InvariantViolation.
400 validation failed (reverse-DNS / length) 404 tenant not found 409 duplicate (platform, package_id) — already registered

No duplicate app per platform. The contract enforced by this endpoint: a tenant may register at most one row per (platform, package_id) pair (FR-AUTH-002 / FR-AUTH-003 operational contract). Soft-deleted (is_active=false) and SUSPENDED rows still hold their index slot, so re-registering the same (platform, package_id) against the same tenant always returns 409. The intended recovery flow is the per-app suspend ↔ reinstate pair — not delete-and-recreate.

POST /v1/admin/tenants/:id/activate
Platform-Admin bearer token

Step 6 of 6. Moves the tenant from Pending to Active. This is the last switch: once flipped, the Institution-Admin's credential from step 3, the signing key from step 4, and the mobile-app allow-list from step 5 can be used together to issue and verify live QR codes. No request body — again, the route :id is the only input.

Notes for QA

CheckWhat to verify
Token reuseA step-1 token expires at expires_in seconds — re-request rather than assume it survives the whole onboarding run.
OrderingSteps 3, 4, 5 and 6 all require a tenantId from step 2; running them out of order returns 404 Tenant not found, not a validation error.
Secret captureRe-running step 3 against a tenant that already has a configuration is a 409, by design — there is no "get me the secret again."
Key preconditionNothing technically stops calling step 6 before step 4. A negative test worth having: activate first, mint the key second, then attempt QR issuance and confirm it still fails cleanly.
Duplicate institutioninstitutionCode is a 6-digit unique key — re-registering the same code is a 409, useful for idempotency checks.
App allow-listA mobile build whose package_id is not on the tenant's /applications list fails closed at /oauth/token with invalid_client / package_mismatch. Skipping step 5 entirely is the most common cause of "fresh tenant, can mint admin token, every device rejected" — the per-app kill-switch suspend / reinstate pair reuses these rows.
Duplicate appRe-running step 5 with the same (platform, package_id) against the same tenant is a 409, even after a soft-delete or SUSPENDED — the unique index ignores is_active and status. The same package_id on a different platform is legal (two rows).
