Who this report is for

You are the team that operates the FI Backend — the mobile/web app your customers use lives in your perimeter, and you deploy this BFF gateway to talk to RVL's sbqr.api on your behalf. The two credentials involved are:

  • RVL platform token — issued by RVL to your FI, used server-to-server. The BFF keeps this in memory; your app never sees it.
  • FI user JWT — issued by your IdP to your end-user, sent by your app on every call (or exchanged once for a hardened auth cookie via POST /v1/auth/login). The BFF verifies it then discards it.

This report covers all seven slices — the BFF is now feature-complete on the v1 scope and ships with BootGuard, contract pinning, resilience, mTLS, cookie auth, and OpenTelemetry export.

What the gateway does today

Inbound — your app calls the BFF

Either an Authorization: Bearer <jwt> header signed by your IdP or a hardened auth cookie minted by POST /v1/auth/login (HTTP-only, Secure, SameSite=Lax, 8-hour fixed lifetime). JWT remains the default; QrProxyController opts into both schemes via [Authorize(AuthenticationSchemes = "Bearer,Cookies")]. No auth = 401. Bad token = 401. Expired token = 401. Wrong audience = 401. Wrong signature = 401.

Outbound — BFF calls sbqr.api (server-to-server)

On startup, the BFF performs client_credentials against /v1/oauth/token using the client_id + client_secret you put in env-vars. It caches the JWT in memory and refreshes it at 80% of its advertised lifetime. With mTLS enabled in Production, the cached PFX is attached via the primary HttpClientHandler. Every response body is validated against the real rvl-secure-bqr-manager/contracts/v1.public.json (camelCase TokenResponse + 4-field GenerateQrResponse + 8-field ValidateQrResponse); contract violations → sanitized 502 ProblemDetails (no PAN leakage).

QR proxy — POST /v1/qr/{generate/{static,dynamic},validate}

Forwards the JSON body verbatim to sbqr.api, attaching the cached platform bearer, the inbound X-Correlation-Id (or a freshly minted one), the inbound user's sub claim as X-User-Sub, and a deterministic Idempotency-Key for the generate endpoints. Wrapped in a Polly v8 pipeline: 5xx and timeouts retry with exponential backoff + jitter (never 401 — that's owned by PlatformAuthHandler, which force-refreshes and retries once).

Observability

Structured Serilog logs with a masking enricher (Authorization, Cookie, Idempotency-Key, PAN, MSISDN, NID, etc. → ***). /health/live + /health/ready JSON probes. OpenTelemetry tracing + metrics via OTLP — gated on OpenTelemetry:Enabled and fail-fast if the endpoint is empty (no silent drop). BootGuard refuses to start in Production with sentinel/placeholder values (set-me-*, example.invalid, missing mTLS path/password).

Slice 5 — Polly 5xx retry

The "PlatformQr" named HttpClient is wrapped in a Polly v8 resilience pipeline that retries on 5xx and HttpRequestException / TaskCanceledException only. 401 is explicitly excluded — that path belongs to PlatformAuthHandler. The fake sbqr.api is run with a toggle that returns 503 on the first three calls to /v1/qr/generate/static and 200 on the fourth.

$ for i in 1 2 3; do
    curl -s -o /dev/null -w "call $i: %{http_code}\n" -X POST \
      http://localhost:8080/v1/qr/generate/static \
      -H "Authorization: Bearer $TOKEN" \
      -H 'content-type: application/json' \
      -d '{"merchantId":"M1","amountMinor":1000}'
  done
# call 1: 503   ← attempt 1 fails, retries 2,3,4 internally
# call 2: 503   ← same
# call 3: 200   ← attempt 4 succeeds → surfaced as 200

Serilog shows three retry events with exponential delays (~200ms, ~400ms, ~800ms with jitter). The caller sees a single 503 OR a single 200 — never partial state.

HTTP/1.1 200 OK
Set-Cookie: .RvL.Sbqr.Auth=; expires=Thu, 01 Jan 1970 00:00:00 GMT; Max-Age=0

Cookie hardening: HttpOnly (no JS access), Secure (HTTPS only), SameSite=Lax, 8-hour fixed lifetime (no sliding). The IdP-issued access token is never stored in the cookie — only the claims extracted from it are signed in.

Security guarantees (verified)

  • client_secret is never logged. Only the exception type name appears in failure logs; the request body is constructed in memory and never stringified to a log sink.
  • The platform JWT never leaves the BFF process. It lives in PlatformTokenManager._accessToken, in process memory, and is only consumed by server-side code (the pre-warm service + PlatformAuthHandler).
  • The debug endpoint exposes state only — never the token value. /debug/platform-token returns { hasToken, expiresAtUtc, lifetimeSeconds, lastRefreshedUtc }. /debug/auth returns { isAuthenticated, userSub } — never the JWT itself.
  • Inbound JWT validation is real, not stubbed. 401s on missing / malformed / wrong-key / expired / wrong-audience tokens are proven by both the unit tests and the live smoke run.
  • Cross-cutting headers are deterministic and audit-friendly. Idempotency-Key is HMAC-derived from (tenant, sub, sha256(body), bucket) — no PII leaks into it. X-User-Sub is the JWT's sub — your opaque user id, not the user's PII.
  • 401-retry doesn't amplify load. At most one retry per request. If the fresh token also 401s, the BFF surfaces 401 to the caller rather than looping.
  • 5xx retries don't conflict with 401-retry. The Polly ShouldHandle predicate checks only >= 500 (and timeout exceptions); 401 is explicitly excluded and belongs to PlatformAuthHandler. Regression-tested.
  • Contract violations never echo PII. ContractViolationFilter returns a sanitized application/problem+json 502 with only the path + schema validation hints — never the upstream body.
  • Cookie hardening. HttpOnly (no JS access), Secure (HTTPS only), SameSite=Lax, fixed 8-hour lifetime (no sliding). The IdP-issued access token is parsed for claims then discarded — the cookie holds only the resolved claims, not the token.
  • OpenTelemetry is fail-fast, not silent. If OpenTelemetry:Enabled=true but OtlpEndpoint is empty, the configurator throws at startup rather than exporting to nowhere.
  • BootGuard refuses to start in Production with placeholder config. set-me-* client id/secret, example.invalid URLs, placeholder salt, missing mTLS credentials → aggregated InvalidOperationException listing every finding.
