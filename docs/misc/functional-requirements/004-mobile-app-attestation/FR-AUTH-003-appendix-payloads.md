## Appendix — Payload-by-payload walkthrough

This section shows the **actual HTTP request and response bodies** for every step, so you
can see exactly what fields your .NET code parses and what it produces. Think of it as
watching the data flow through each wire.

### Step 1 — App requests a nonce

> **Need the full app-side flow?** See [How the app gets its JWT token —
> step by step](./FR-AUTH-003-production-operations.md#how-the-app-or-sdk-gets-its-jwt-token--step-by-step)
> in the Production & Operations guide for the complete 3-call sequence.

**What the app sends:**

```http
GET /v1/oauth/attestation-nonce
Authorization: Basic base64("dhb-android-app:the-embedded-secret")
```

> Note: this reuses the **same credential** the app already uses for `POST /v1/oauth/token`.
> The `client_id` and `client_secret` are the same ones from the `tenant_configurations`
> row. You verify them with the same Argon2id check.

**What your backend returns:**

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "nonce": "x7y9q2m4p1r8s3t6"
}
```

**What your code does:**
- Parse the `Authorization: Basic` header (or the `client_id`/`client_secret` body fields).
- Look up the `tenant_configurations` row by `client_id`.
- Argon2id-verify the secret.
- Generate a random nonce (e.g. `Guid.NewGuid().ToString("N"[..16])`).
- Store it in Redis (or a table) with a 5-minute TTL and a "used: false" flag.
- Return it as JSON.

**The in-memory command your handler dispatches:**

```csharp
// MediatR command
var result = await mediator.Send(new IssueAttestationNonceCommand(
    ClientId: "dhb-android-app",
    ClientSecret: "the-embedded-secret"));

// result.Value is the nonce string: "x7y9q2m4p1r8s3t6"
```

### Step 2 — App gets the Google/Apple signed proof (what your backend receives)

The mobile SDK calls Google's Play Integrity API with the nonce. Google returns a **JWT**
signed with Google's private key. The app base64-encodes that JWT and sends it to your
enrollment endpoint.

**What the app sends to your `POST /v1/oauth/device-enrollment`:**

```http
POST /v1/oauth/device-enrollment
Authorization: Basic base64("dhb-android-app:the-embedded-secret")
Content-Type: application/json

{
  // "android" or "ios" — your backend routes to the right verifier
  "platform": "android",

  // The app's package name (same string from the token request)
  "package_id": "com.dhakabank.app",

  // The base64-encoded Google-signed verdict JWT (opaque to the app, but
  // YOUR backend decodes and verifies this)
  "attestation_verdict": "eyJhbGciOiJFUzI1NiIsImtpZCI6Ikdvb2dsZVB1Yl...",

  // The device's public key (generated by the SDK in the Android Keystore /
  // iOS Secure Enclave — the private key NEVER leaves the device)
  "device_public_key": "-----BEGIN PUBLIC KEY-----\nMFkwEwYHKoZIzj0CAQYIKoZIzj0DAQcDQgAE...\n-----END PUBLIC KEY-----"
}
```

#### What the attestation verdict JWT contains (decoded)

Your `GooglePlayIntegrityVerifier` decodes this JWT. Here is its **payload** (the part
between the two dots of the base64):

```json
{
  "iss": "https://android.play.googleapis.com",
  "aud": "1234567890:android:abcdef",
  "exp": 1694726400,
  "iat": 1694722800,
  "nonce": "x7y9q2m4p1r8s3t6",
  "package_name": "com.dhakabank.app",
  "certificate_sha256_digest": "9e3a1b2c4d5e6f7a8b9c0d1e2f3a4b5c6d7e8f9a0b1c2d3e4f5a6b7c8d9e0f1a",
  "app_recognition_verdict": "PLAY_RECOGNIZED",
  "device_recognition_verdict": "MEETS_DEVICE_INTEGRITY",
  "request_hash": "x7y9q2m4p1r8s3t6"
}
```

**Your verifier checks:**
- ✅ `iss` = `https://android.playintegrity.googleapis.com` (or the test issuer in QA)
- ✅ `nonce` == the nonce you issued in Step 1 (and not already used)
- ✅ `exp` is within `VerdictMaxAgeMinutes`
- ✅ `package_name` == `com.dhakabank.app` (matches the app's claim)
- ✅ `certificate_sha256_digest` == `9e3a1b...` (matches the `signing_cert_sha256` column)
- ✅ `app_recognition_verdict` == `PLAY_RECOGNIZED`
- ✅ `device_recognition_verdict` indicates a genuine device

If any check fails → `invalid_client` (same error as every other rejection).

**What your backend returns on success:**

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "device_id": "c3d4e5f6-7890-abcd-ef12-345678901234",
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type": "Bearer",
  "expires_in": 600
}
```

#### The decoded access token (what the app stores)

```json
{
  "sub": "device:c3d4e5f6-7890-abcd-ef12-345678901234",
  "tenant_id": "a1b2c3d4-...",
  "scope": ["qr:generate", "qr:validate"],
  "cnf": {
    "x5t#S256": "sha256-of-the-device-public-key-thumbprint"
  },
  "iss": "sbqr",
  "aud": "sbqr-api",
  "exp": 1726307612,
  "nbf": 1726307412
}
```

**Key things to notice:**
- `sub` is `device:{guid}` — this is the **device id**, not a tenant credential.
- `cnf` (confirmation) claim contains the device key thumbprint. **This is the PoP binding.**
- No `package_id` — that was validated during enrollment, not stored in the token.

### Step 3 — App calls a QR endpoint (with PoP signature)

**What the app sends:**

```http
POST /v1/qr/generate/static
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
X-Signature: v1=MEUCIQD...base64-of-signature...
X-Timestamp: 1694726412
Content-Type: application/json

{
  "name": "AreebaNawar",
  "account": "01711111111",
  "amount": "500.00"
}
```

The `X-Signature` is over this string:
```
POST /v1/qr/generate/static 1694726412 sha256-base64-of-the-json-body-above
```

Signed with the device's **private key** (which only exists inside the phone's secure
hardware).

**What your backend does (in the `OnTokenValidated` event):**

```csharp
// 1. The JWT is already validated (signature, expiry, issuer, audience).
// 2. The token has a "cnf" claim → PoP is required.
// 3. Reconstruct the signed payload:
var payload = $"{httpMethod} {path} {timestamp} {bodyHash}";

// 4. Look up the device's PUBLIC key from enrolled_devices (by thumbprint).
var devicePublicKey = await _devices.GetPublicKeyByThumbprintAsync(thumbprint, ct);

// 5. Verify the signature.
if (!CryptoHelper.VerifySignature(devicePublicKey, payload, signature))
{
    ctx.Fail(new SecurityTokenException("Invalid PoP signature"));  // → 401
    return;
}

// 6. Proceed to the QR generation handler.
```

**What your backend returns:**

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "qr_payload": "00010A01940016bd.org.bb.npsb0100010091711111111305405058901017AreebaNawar013000000500.00500..."
}
```

### Attack scenario 1 — stolen credentials, no attestation

```http
POST /v1/oauth/device-enrollment
Authorization: Basic base64("dhb-android-app:the-embedded-secret")
Content-Type: application/json

{
  "platform": "android",
  "package_id": "com.dhakabank.app",
  "attestation_verdict": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.fake.Jw",   ← forged, not Google-signed
  "device_public_key": "-----BEGIN PUBLIC KEY-----\n..."
}
```

```http
HTTP/1.1 401 Unauthorized
Content-Type: application/json

{
  "error": "invalid_client"
}
```

**Your verifier tries to verify the JWT signature with Google's public key → fails.**
Same generic `401 invalid_client` error. The attacker learned nothing.

### Attack scenario 2 — stolen token, no device key (Postman replay)

```http
POST /v1/qr/generate/static
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...   ← stolen token
X-Timestamp: 1694726412
Content-Type: application/json
                                              ← NOTE: no X-Signature header

{
  "name": "AreebaNawar",
  "account": "01711111111",
  "amount": "500.00"
}
```

```http
HTTP/1.1 401 Unauthorized
Content-Type: application/json

{
  "error": "invalid_token"
}
```

**Your middleware sees the `cnf` claim → requires `X-Signature` → it's missing → 401.**
The stolen token is useless without the private key that lives on the user's phone.

### Attack scenario 3 — tampered APK (wrong signing cert)

The attacker decompiles the app, changes some code, re-signs it with their own certificate,
and installs it. The package name is still `com.dhakabank.app`, but the signing certificate
is different.

```json
// The attestation verdict Google returns:
{
  "package_name": "com.dhakabank.app",
  "certificate_sha256_digest": "DIFFERENT_FROM_9e3a1b...",   ← attacker's cert, not the registered one
  "app_recognition_verdict": "PLAY_RECOGNIZED",               ← package name still matches...
  ...
}
```

Your enrollment handler checks:
```csharp
// The verdict's signing cert digest ≠ the signing_cert_sha256 column on tenant_applications
if (verdict.SigningCertSha256 != appRow.SigningCertSha256)
{
    return Fail("verdict_app_mismatch");  // → 401
}
```

### Attack scenario 4 — old device that needs re-attestation

After 7 days (`ReattestationPeriodDays`), the device must re-prove itself:

```http
POST /v1/oauth/device-enrollment
Authorization: Basic base64("dhb-android-app:the-embedded-secret")
Content-Type: application/json

{
  "platform": "android",
  "package_id": "com.dhakabank.app",
  "attestation_verdict": "<fresh Google verdict>",
  "device_public_key": "-----BEGIN PUBLIC KEY-----\n...same key as before..."
}
```

If valid:
```http
HTTP/1.1 200 OK
{
  "device_id": "c3d4e5f6-7890-abcd-ef12-345678901234",  ← same device_id
  "access_token": "eyJ...",                            ← new token
  "token_type": "Bearer",
  "expires_in": 600
}
```

Your handler updates `attestation_verified_at` and `attestation_verdict` on the existing
`enrolled_devices` row rather than creating a new one.

### How your C# classes map to these JSON payloads

| JSON payload | Your C# class | File |
|---|---|---|
| `POST /v1/oauth/attestation-nonce` request | `IssueAttestationNonceCommand` | `.../Commands/IssueAttestationNonce/IssueAttestationNonceCommand.cs` |
| `POST /v1/oauth/attestation-nonce` response `{nonce:"..."}` | `IssueAttestationNonceResult` | same folder |
| `POST /v1/oauth/device-enrollment` request | `EnrollDeviceCommand` | `.../Commands/EnrollDevice/EnrollDeviceCommand.cs` |
| `POST /v1/oauth/device-enrollment` response | `EnrollDeviceResult` | same folder |
| `POST /v1/oauth/token` request (FR-AUTH-002, extended) | `TokenRequest` | `.../Api/Contracts/TokenRequest.cs` |
| `POST /v1/oauth/token` response | `TokenResponse` | `.../Api/Controllers/OAuthController.cs` |
| Decoded verdict fields | `AttestationVerdict` record | `.../Application/Abstractions/IAttestationVerifier.cs` |
| Access token claims (decoded JWT) | `AccessTokenClaims` | `.../Application/Abstractions/IAccessTokenIssuer.cs` |
| The `enrolled_devices` table | `EnrolledDevice` aggregate | `.../Domain/Aggregates/EnrolledDevice.cs` |
| The `tenant_applications` table | `TenantApplication` aggregate (existing) | `src/Modules/Tenancy/Domain/Aggregates/` |

**The key insight for a .NET developer:** You never call Google or Apple APIs
yourself. The mobile SDK does that. Your backend receives a **blob** (base64 string) in
the `attestation_verdict` field. Your `IAttestationVerifier.VerifyAsync()` method:
1. Downloads the provider's **public key** (Google publishes it at a well-known URL).
2. Verifies the blob's **signature** with that public key.
3. Reads the **payload** (package name, cert digest, nonce, verdict) and checks each field.
4. Returns a normalized `AttestationVerdict` record.

The verifier is the only piece that needs to know how to talk to Google/Apple. Everything
else works with the clean `AttestationVerdict` record.
