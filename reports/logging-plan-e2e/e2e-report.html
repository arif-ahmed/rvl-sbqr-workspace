7. Investigation playbook for developer / ops

This is the runbook a developer or on-call ops engineer follows when a complaint comes in. Every anchor below corresponds to one of the investigation anchors A–E in docs/logging-plan.md §4. All SQL/queries are run against the production read replica. Example correlation IDs come from the e2e run above so the playbook can be drilled without staging.

Anchor A — "I want to see exactly what happened on a single request."
You have either the correlation_id (from the customer or the bank's gateway logs) or the payload_hash (from the bank's internal log).
  1. Pull every line from the manager log with that correlation_id: 
    zgrep "$corr_id" logs/api-stdout.log
    You will see the full canonical summary line (method, path, tenant_id, payload_hash, qr_type, verdict, reason_code, request_id, status, duration) plus every MediatR handler log emitted inside the scope. W3C TraceId/SpanId in the Scopes array lets you pivot into any downstream trace collector (Jaeger / Application Insights) and see the DB and HTTP fan-out.
  2. Cross-check via payload_hash: 
    zgrep "$payload_hash" logs/api-stdout.log
    Because payload_hash is unique per received bytes, it tells you whether the same QR was ever seen by the platform (and therefore which tenants signed which versions).
  3. If the complaint is about a specific time window, narrow with --since / --until flags on your log shipper.
Anchor B — "The verifier said CRC_MISMATCH / REPLAY_DETECTED / MALFORMED_TLV — is this a customer-side bug or a platform issue?"
Use the reason_code field. The mapping is locked in SBQR.Modules.Verification.Domain.VerdictReasonCode:
reason_codeMeaningAction
CRC_MISMATCHthe customer scanned a QR whose CRC tag does not match the body — payload was corrupted in transit, on the customer's device, or printed badlyask the bank to re-print / re-issue; do not retry the verify call
MALFORMED_TLVthe bytes are not a valid BanglaQR TLV stream — typically a foreign QR (Dana, PromptPay, bKash…) was scannedno platform action; educate the merchant
REPLAY_DETECTEDthe same request_id was seen inside the replay windowplatform working as designed; explain to caller
SIGNATURE_INVALIDEd25519 verification failedraise a Sev-2 incident — possible key compromise or vendor mis-config
UNKNOWN_ISSUERthe issuing institution code is not in the trust listopen a trust-list ticket; check institution_trust_directory freshness
Anchor C — "I need a tamper-evident audit trail for a regulator / legal request."
Use the audit_logs table. Two join keys are guaranteed to link logs ↔ audit rows:
  1. correlation_id: every handler that performs a domain action writes one audit_logs row whose metadata->'correlation_id' equals the request's correlation_id. So: 
    SELECT id, action, resource_id, occurred_at, prev_hash, row_hash
FROM audit_logs
WHERE metadata->>'correlation_id' = '$corr_id'
ORDER BY occurred_at;
    This gives you the complete sequence of state-changing actions the platform performed for that one request.
  2. payload_hash: stored in resource_id for QR generation rows. So a regulator that only has the payload hash (e.g. from a printed QR) can ask: 
    SELECT metadata
FROM audit_logs
WHERE resource_id = '$payload_hash'
  AND action = 'QR_GENERATED';
    and get the issuing tenant, institution code, signing key version, and the original correlation_id back.
  3. Chain integrity: audit_logs is hash-chained (prev_hash, row_hash). To prove no row was tampered with between regulator request and now: 
    SELECT
    lag(row_hash) OVER (ORDER BY occurred_at) = prev_hash AS chain_ok,
    *
  FROM audit_logs
  WHERE tenant_id = '$tenant_id'
    AND occurred_at BETWEEN '$start' AND '$end'
  ORDER BY occurred_at;
    Every row should return chain_ok = true; a single false is a Sev-1 incident.
Anchor D — "The customer got a 5xx / the bank's gateway is throwing a timeout — where is the bottleneck?"
Two places to look:
  1. The canonical summary line has Duration in milliseconds — filter the log shipper for requests over the SLO (default 300 ms): 
    jq -c 'select(.State.Duration > 300)
            | {corr:.State.correlation_id, ms:.State.Duration,
               path:.State.Path, status:.State.StatusCode}'
       < logs/api-stdout.log
  2. Hand the W3C TraceId to the tracing backend. Every scope in the JSON log includes {"SpanId":"…","TraceId":"…","ParentId":"…"}, so the trace will show: HTTP receive → correlation middleware → MediatR pipeline → key-custody vault decrypt → DB round-trips → response. The longest span is the bottleneck.
Anchor E — "We suspect a key was misused or a request came from somewhere it shouldn't have."
Pivot on tenant_id: 
jq -c 'select(.State.tenant_id == "$tid")
        | {at:.Timestamp, corr:.State.correlation_id,
           path:.State.Path, status:.State.StatusCode}'
     < logs/api-stdout.log

Cross-check the same window in the auth gateway. A spike in qr:generate tokens issued for this client_id without a matching /v1/qr/generate/* summary line is the classic "credential exfil" pattern and warrants rotating the client secret via the IdentityAccess admin endpoint.

9.1 Scenario

Customer complaint (from Dhaka Bank): "My static QR printed at the ATM failed validation yesterday with CRC_MISMATCH. Did we print it wrong?"

  1. Investigator mints an OAuth token for the bank.
  2. Re-runs the same generation with a fresh idempotency key to capture a fresh payload_hash.
  3. Tampers the last 4 bytes of the CRC tag (mimicking the customer's broken print), sends to /v1/qr/validate with the customer's request_id, attaches a custom X-Correlation-Id so the investigator can pivot later.
  4. Re-submits the identical request to prove the replay-detection path works on this exact payload.
  5. Then runs Anchor A / A2 / C / C2 / C3 / E commands against the captured log and the live database.

ANCHOR C3 — hash-chain integrity

$ psql ... -c "
  SELECT COUNT(*) FILTER (WHERE chain_ok) AS ok_rows,
         COUNT(*) FILTER (WHERE NOT chain_ok) AS broken_rows
  FROM (
    SELECT lag(entry_hash) OVER (ORDER BY created_at) = previous_hash AS chain_ok
    FROM audit_logs
    WHERE tenant_id = (SELECT tenant_id FROM tenants WHERE institution_code='000085')

  broken_rows= 0

Investigator note: Every audit row's entry_hash matches the previous_hash of its predecessor. No tamper. This is the line of evidence a regulator or court would cite to prove the platform's audit trail is intact for tenant 000085.

9.3 Outcome of the live investigation

Verdict for the bank: The customer's printed QR had a corrupted CRC tag (last 4 bytes were zeroed instead of carrying the real CRC). The platform correctly rejected the first scan as CRC_MISMATCH and any subsequent scan as REPLAY_DETECTED. The customer needs to re-print. The platform's audit trail is intact and the signing key is fine (Ed25519 signature over a fresh re-issue verifies as VALID).

No platform action required. The customer complaint is closed with reference correlation_id=2a0d2336-853c-495b-bc28-56d0dffef875 and the canonical summary line above.
